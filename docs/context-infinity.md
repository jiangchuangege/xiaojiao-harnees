# 无限 7 · 上下文无限（对话能一直聊下去，不撞窗口）

> 代码落点：`xiaojiao_app.py` 的 `_max_context_tokens()` / `_estimate_tokens()` /
> `_fit_context()` / `_history_digest()`；日志 `logs/context_fit.log`
> 自测：`tools/test_single_request_limit.py`（无限 6，真 HTTP + 100 轮压测）

---

## 1. 它要解决的问题

本地大脑的上下文是一个**物理上限**：`brain.llama.ctx = 20224`。

一旦拼好的 `system + history + 本轮问题` 超过它，llama-server 直接报：

```
request (22562 tokens) exceeds the available context size (20224 tokens)
```

用户看到的是一个 400/500，然后这轮就没回答。

主流解法是"扩 ctx"。小焦不扩 —— 因为本地显存就那么大，扩不动；
而且**扩 ctx 只是把墙往后挪，墙还在**。所以它做的是另一件事：

> **不扩上限，改"装配什么进去"。** 让对话长度不受窗口限制 —— 这就是"上下文无限"。

---

## 2. 核心：四层防护

| 层 | 做什么 | 代码 |
|---|---|---|
| **上限校准** | 算准"这一轮到底有多少 token 可用" | `_max_context_tokens()` |
| **计量** | 零依赖估算 token，**宁可高估** | `_estimate_tokens()` |
| **滑动窗口 + 硬性截断** | system 与本轮问题**永远保留**；历史从最老一端开始丢 | `_fit_context()` |
| **摘要压缩** | 更早的轮次**压成摘要**，最近 4 轮留原文 | `_history_digest()` |

---

## 3. 每一层为什么这么设计

### 3.1 上限校准：`_max_context_tokens()`

优先读操控文件 `capabilities.max_context_tokens`；否则按引擎取
（本地 = `brain.llama.ctx`，云端 = 128000），再减去安全余量（默认 1000）。

**这里有一个实测踩出来的坑：`ctx` 必须校准。**

llama-server 收到 `-c 20000`，**实际给的却是 20224** ——
llama.cpp 会把 `n_ctx` **向上取整到 256 的倍数**（20000 / 256 = 78.125 → 79 × 256 = 20224，
实测 `GET http://127.0.0.1:5801/props` 返回 `n_ctx = 20224`）。

所以操控文件里**直接写 20224**（本身就是 256 的倍数，不会被再取整）。
不校准的后果是：载体按 19000 算上限，白白浪费 1224 token 的窗口 ——
明明能装下的一轮对话，被载体自己判成"装不下"。

### 3.2 计量：`_estimate_tokens()`

不引第三方分词器（零依赖），按经验估：中文 &lt;汉字&gt; ≈ **1.5 token/字**，ASCII 约 3 字符 ≈ 1 token。

**为什么是 1.5 而不是 1.05** —— 这是实测校准出来的：

> 原来按 1.05 算，**低估约 40%**；`_fit_context` 报告"合计 4216 / 上限 19500"，
> 而实际请求是 **22562 token** —— 直接撞 400/500。

**判据是单向的：宁可高估**（代价只是少留几轮历史），**绝不低估**（一旦低估就是硬报错）。
这也是为什么整个模块不用精确分词器：高估一点点比引入一个依赖更划算。

### 3.3 滑动窗口 + 硬性截断：`_fit_context()`

**取舍优先级是死的**，不随情况浮动：

1. **system（人格 / 铁律）永远不能丢** —— 丢了就不是小焦了；
2. **本轮问题永远不能丢** —— 丢了就没在回答这个问题；
3. 能丢的只有"**更老的历史**"，而且**从最老的一端开始丢**；
4. 再丢也要保住 `min_history_rounds` 轮（默认窗口 10 轮，下限 2 轮）。

**另一个实测踩出来的坑：`reserve` 必须算上工具 schema。**

function-calling 要把 77 个工具的 JSON 声明一起发出去，那是**几千 token**。
上一版漏算它，于是裁剪完**仍然超限** —— 裁了历史却还是报错，看起来像"裁剪没生效"。

说明文本按这个格式输出，让"为什么超"一眼可查，而不是让用户面对一个语焉不详的 400：

```
system=a + tools=b + history=c + 本轮=d = 合计 f / 上限 g
```

### 3.4 摘要压缩：`_history_digest()`

保住下限的那几轮之后，再往前的轮次**不直接扔**，而是压成摘要：

- 最近 `HISTORY_KEEP_FULL = 4` 轮：**留原文**（这几轮最可能是"我刚才说的"）；
- 更早的：每轮压成一行 60 字（`- 用户：…` / `- 我：…`），最多留 12 行；
- 注入时带一句「（更早的那些轮次已经压成摘要，原文不再占窗口）」——
  让模型知道**这是摘要、不是原话**，避免它把摘要当成用户原话复述。

---

## 4. 它和无限 1、无限 6 的分工

三个看着像，其实管的是三件不同的事：

| | 管什么 | 谁在做 |
|---|---|---|
| **无限 1 · 记忆无限** | 历史**存在哪** | 全部历史永久落盘（`logs/xiaojiao_memory_vec.jsonl`），要用时按需检索 top-K |
| **无限 7 · 上下文无限** | 这一轮**装什么进去** | 摘要 + 最近 N 轮原文 + 按需检索的记忆，拼进有限窗口 |
| **无限 6 · 单次请求永不超** | 装完之后**绝不超限** | 发之前算 token，超了从最老的历史砍 |

一句话：**无限 1 保证"记得住"，无限 7 保证"聊得下去"，无限 6 保证"发得出去"。**

三者合起来才是那句"对话能一直聊下去"：原文留在硬盘上（无限 1），
窗口里只放最近几轮加摘要（无限 7），发之前再验一次不超限（无限 6）。

## 5. 实测

| 项 | 实测 |
|---|---|
| ctx 校准 | `-c 20000` → `n_ctx = 20224`（256 的倍数向上取整） |
| token 估算校准 | 低估版报"合计 4216 / 上限 19500"，实际请求 **22562** → 改 1.5 token/字 |
| 100 轮压测 | 连问 100 轮**不报 ctx 错**（`tools/test_single_request_limit.py`） |
| 裁剪可见性 | `logs/context_fit.log` 每次裁剪都留 `system=a + tools=b + … = 合计 f / 上限 g` |

## 6. 如实标注（没做到的）

1. **窗口里仍然只装得下有限的内容。** "上下文无限"说的是**对话可以无限长**，
   不是"窗口无限大"—— 装不下就是装不下，靠的是摘要与丢弃顺序，不是魔法。
2. **估算不是精确值。** 1.5 token/字是实测校准的经验值，
   不同文本（大量代码、大量标点）会有偏差。取向上偏差是为了安全，代价是会**过早开始丢历史**。
3. **摘要会丢信息。** 每轮压到 60 字、最多 12 行，丢掉的细节**不会回来**。
   要找细节只能靠无限 1 的按需检索 —— 而那是**按相关性**找的，不保证找得回全部。
4. **`HISTORY_KEEP_FULL = 4` 是人为取值**（"最近 4 轮留原文"），不是算出来的最优点。
5. **裁剪顺序是"从最老丢"这种最朴素的做法。** 没有做重要性加权
   （比如"这条历史里含用户的名字"就留下）——那是可以更好、但现在没做的地方。
