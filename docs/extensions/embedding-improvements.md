## 1. 这份文件是什么

这是「小脑嵌入编码」的**可选扩展点**文档。它记录的是一组**未来可选**的改进方向，
不是待办清单，也不是当前版本的组成部分。

## 2. 非必要（**本文第 1、2 条已按实测更正**）

> ⚠️ **2026-09-16 更正**：本节原来写的是「本文件里的五个方向，当前版本**一个都没有接入**」——
> **这句是错的**，而且**和本文第 57 行自相矛盾**（那里早就写着"方向 1 已落地（默认启用）"）。
> 实测（`core/embedder.py` 的 `_MV_MIN = 200`）：
> **长于 200 字的文本默认就会算首/中/尾三个向量**，代码里**没有任何开关**，
> `memory_vec.add_memory()` 每次都调 `embed_parts()`。所以：

- **方向 1（多向量编码）已经落地，而且默认就是开着的** —— 不需要任何配置，也不"可选"。
  实测：文本 200 / 400 / 800 字 → 返回 `head/mid/tail`；50 字 → 退回 `full`（短文本没有首中尾可分）。
- **方向 2–5 才是"可选、未接入"**（按句切分 / U 型位置权重 / 语义适配层 / 换更强的嵌入模型）。
- **当前方案已够日常使用**：单向量 + 长文本"首/中/尾"分块 + 末块加权，日常对话与记忆检索够用。
- **本文其余方向不接入，不影响任何现有功能**：七个无限、记忆三层、医生、精排等都不依赖它们。

## 3. 什么时候才需要看这份文档

满足**任意一条**再往下看：

- 用户的日常输入以长文本为主（单条超过 500 字）
- 现有编码方案不够用了（检索结果明显对不上）
- 想进一步优化检索精度

**三条都不满足就别动，当前方案够用。**

## 4. 当前状态

| 项 | 现状 |
| --- | --- |
| 编码形态 | 单向量编码，512 维 |
| 长文本 | 按 96 字切块逐块编码，末块加权（权重 20），保证尾部不丢 |
| 短文本 | 不分块（只分 1 块），与不分块时逐位相同 |
| 实测 | 前 500 字相同、结尾不同：0.9999 → 0.9889 |

## 5. 已知限制

- **长文本首尾不能同时被同等重视**：当前偏向尾部（6 块时末块约占 81%），拿长记忆的**开头**去检索会变弱。
- **字符级模型语义区分弱**：这是本质限制。「天气很好」与「下雨了」共享「今天」两个字，
  字符级模型看到的是同一个字串，不是相反的意思。反义与无关两条阈值因此不达标。

载体的现有补偿是分工：小脑负责召回，大脑负责精排（`core/retriever.py` 的 `rerank` 相关逻辑）。

## 6. 可选扩展方向

每个方向都写清四件事：**是什么**、**用了能扩展到哪**、**适合什么场景**、**代价与解决不了什么**。

### 方向 1 · 多向量编码 —— **已落地（默认启用）**

> 状态：**已落地**。2026-09-15 上线，短文本（小于 200 字）不写多向量，行为与单向量一致。
> 实测：用开头查 / 中段查 / 结尾查**都能命中**长记忆（top-1）。
> 实现：`core/embedder.py` 的 `embed_parts`（段内用纯均值，不做位置偏置）、
> `core/memory_vec.py` 的 `vectors` 字段与「max 取最高分」打分。

- **是什么**：一条长记忆存 head / mid / tail 三个向量。
- **用了能扩展到哪**：
  - 长文本首尾都能被检索到
  - 不再牺牲开头
  - 从「偏向尾部」扩展到「**首尾都保留**」
- **适合场景**：用户大量输入长文本（单条超过 500 字）
- **代价**：存储 ×3，检索 ×3
- **解决不了**：语义区分（仍是字符级）

### 方向 2 · 按句切分

- **是什么**：按中文标点切句，每句一个向量。
- **用了能扩展到哪**：
  - 每句话都能被独立检索
  - 短句内容不被长句稀释
  - 从「整体编码」扩展到「**逐句编码**」
- **适合场景**：用户输入以多句组成
- **代价**：短句合并逻辑要处理
- **解决不了**：语义区分

### 方向 3 · U 型位置权重

- **是什么**：首尾都加权，中间低。
- **用了能扩展到哪**：
  - 首尾同时保留，**不改存储**
  - 从「只顾尾」扩展到「**首尾均衡**」
- **适合场景**：想快速改善，不想大改
- **代价**：中间内容可能被稀释
- **解决不了**：中间内容的检索精度

### 方向 4 · 语义适配层

- **是什么**：小脑输出后过一层 MLP，用对比学习训练。
- **用了能扩展到哪**：
  - 语义区分能力部分提升
  - 从「字符级语义」扩展到「**准语义级**」
  - 能区分「很好 / 不错」与「很好 / 下雨」
- **适合场景**：有标注数据（正例对、负例对）
- **代价**：需要训练数据 + 训练时间
- **解决不了**：完全替代大脑精排

### 方向 5 · 换更强的嵌入模型

- **是什么**：例如用 `bge-small-zh` 之类的语义编码器替换小脑编码。
- **用了能扩展到哪**：
  - 语义区分接近专业水平
  - 从「字符级」扩展到「**专业语义级**」
  - 检索精度大幅提升
- **适合场景**：愿意放弃「自研」卖点，追求最高精度
- **代价**：丢掉小脑「学」的能力
- **解决不了**：小脑的成长性就没了

## 7. 如何选择

| 你的情况 | 建议 |
| --- | --- |
| 日常场景 | 当前方案够用，不用看这份文档 |
| 长文本为主 | **方向 1 已落地，无需再选**；仍不够再考虑方向 2 |
| 想快速改善 | 方向 3 |
| 有训练数据 | 方向 4 |
| 不介意换模型 | 方向 5 |

## 8. 原则

- 不是「现在做」，是「**未来可选**」—— **只对方向 2–5 成立**；
  **方向 1（多向量编码）已经落地并且默认启用**，不属于"可选"（见第 2 节与第 57 行）
- 每个方向**独立**，可以叠加
- **方向 2–5 非必要、默认不启用**（方向 1 不是）
- 有需求时按图扩展
