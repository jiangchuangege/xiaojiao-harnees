| 项目 | 内容 |

## 摘要

小焦把每个模型注册成一颗"大脑"，由调度中心决定任一时刻哪一颗占用显存。
本文说明调度的对象、状态机、切换路径、两套切换机制的职责划分，以及"秒级"成立的前提。

## 1. 术语

本仓库里"大脑""小脑""火种"指三件不同的东西，先约定清楚，后文不再混用。

| 术语 | 含义 | 对应代码 |
|---|---|---|
| 大脑 | 一个可独立服务的模型（聊天、编码、视频、播客、云端视频），每颗有名称、端口、类型与状态 | `brain_manager.BRAINS` |
| 调度中心 | 负责卸载与加载大脑、让出与恢复显存的逻辑层，是小焦自己的组件 | `brain_manager.py`、`video_service/model_switch.py` |
| 火种 | 一次 HTTP 请求的目的地，即"当前用哪个模型端点"，可热插拔 | `core/carrier/brain_registry.py` |
| 小脑 | 自研的 MiniGPT（`xiaojiao_harness.py`），负责轻量判断与离线兜底，与本文的多大脑调度不是同一件事 | `xiaojiao_harness.py` |

调度中心不等于小脑。原文档把调度层称作"小脑"与仓库的既有命名冲突，本文按上表统一。

## 2. 背景与问题

小焦需要在一次会话里提供聊天、编码、视频、播客与音乐能力，而单张消费级显卡放不下全部模型。
直接按需"杀进程再启动"能省显存，但每次切换都要重新读盘加载权重，等待时间长。
此外，"当前用哪个模型"这件事原本散落在控制文件、环境变量与启动脚本里，
没有统一的地方可以查询"有哪些模型、现在用哪个、挂了怎么办"。

## 3. 设计目标

- 任一时刻最多一颗大脑占用显存，避免双模型驻留导致显存溢出。
- 最近使用过的大脑留在内存，切回时不重新读盘。
- 切换不重启主进程，会话、记忆、工具与配置都不受影响。
- 新增一颗大脑只改配置与注册表，不改调度逻辑。
- "当前用哪颗模型"可查询、可切换、可在故障时自动兜底。

## 4. 架构与原理

### 4.1 一次本地视频生成中的完整路径

以"用户要求生成一段视频"为例，各角色按下列顺序参与：

| 步骤 | 参与方 | 动作 |
|---|---|---|
| 1 | 用户界面 | 提交场景描述，产生一个任务 |
| 2 | 提示词精炼 | 查询小脑向量库；未命中则让当前大脑改写提示词，并写回向量库 |
| 3 | 调度中心 | 调 `switch_to("video")`：处于温存状态的其他大脑被彻底卸载，当前运行的大脑转入温存 |
| 4 | 显存协调 | 启动 ComfyUI，等待 8188 端口就绪（上限 240 秒） |
| 5 | 视频大脑 | 载入工作流，做扩散采样，按 `ComfyUI /progress` 回报步数 |
| 6 | 显存协调 | 产物落盘后调 `switch_to("chat")`，恢复聊天大脑 |
| 7 | 结果 | 用户界面播放视频；若未开启常驻，启动 15 分钟闲置释放计时 |

失败路径同样会尝试第 6 步，保证聊天大脑不至于一直缺席。

### 4.2 大脑注册表

`brain_manager.BRAINS` 是一个字典，键即大脑标识。当前登记五颗：

| 键 | 名称 | 端口 | 类型 |
|---|---|---|---|
| `chat` | 聊天大脑（Qwen 4B，llama-swap） | 9292 | `llama` |
| `video` | 视频大脑（Wan2.1 加 ComfyUI） | 8188 | `comfy` |
| `coder` | 编码大脑（Qwen3-8B） | 9292 | `llama` |
| `podcast` | 播客大脑（写稿、配音、封面） | 5000 | `podcast` |
| `agnes` | 云端视频大脑（Agnes，免费档） | 无 | `cloud` |

每项包含名称、端口、类型、一个 `vram_gb` 估算值与状态。估算值只供监控页展示，
并非实测占用。增加一颗大脑的做法是在该字典里加一项；若类型是 `llama` 或 `comfy`，
现有调度代码即可处理，其他类型需要自行实现启动逻辑。

### 4.3 状态机

| 状态 | 含义 | 进入方式 |
|---|---|---|
| `SLEEP` | 初始状态，未加载 | 注册表初始值 |
| `RUN` | 权重在显存，正在服务 | `wake()` 成功后设置 |
| `WARM` | 权重在内存，进程仍在 | `sleep()` 设置 |
| `OFF` | 已彻底卸载，显存与内存都不占 | `_full_stop()` 设置 |

`switch_to(target)` 的状态迁移分三步执行，全程持一把锁：

1. 遍历注册表，把处于 `WARM` 且不是目标的大脑彻底卸载（`_full_stop()`）。
   这一步保证内存里只留一颗温存模型。
2. 把当前处于 `RUN` 且不是目标的大脑转入温存（`sleep()`）。
3. 唤醒目标（`wake()`），返回 `{"switched", "from", "ok"}`。

### 4.4 让位与恢复

`video_service/model_switch.py` 是显存协调器，负责与具体服务打交道：

| 函数 | 作用 |
|---|---|
| `stop_brain()` | 优先调 llama-swap 的卸载接口 /api/models/unload/xiaojiao，失败时回落到按端口找进程并结束它 |
| `start_brain()` | llama-swap 在线时触发一次请求让它按需加载；否则直接启动 llama-server |
| `start_comfy()` | 按便携版的解释器优先级启动 ComfyUI，等待 8188 就绪，必要时加 `--lowvram` |
| `stop_comfy()` | 结束 ComfyUI；`keep_warm` 为真时保留进程不杀 |
| `get_state()` | 不持锁返回状态副本，避免状态查询被长耗时操作堵住 |

## 5. 火种登记处

`core/carrier/brain_registry.py` 解决的是另一个问题：模型端点的登记、探测与兜底。
它与调度中心的分工是——调度中心管"显存里放哪颗模型"，登记处管"这次请求发往哪个端点"。

### 5.1 配置来源与兼容

配置取 `xiaojiao_control.json` 的 `brains` 字段（列表或字典均可），当前模型取 `active_brain`。
没有 `brains` 时会尝试从旧写法里凑出火种：`models` 列表按各项的 `name` 登记，
`brain.api` 登记为名为"默认大脑"的一项。

`Brain.from_config()` 同时接受两套字段名：`base_url` 与 `url`、`api_key` 与 `key`、
`kind` 与 `local`。都没有线索时按地址猜测，命中本机或内网特征即判为本地。
配置读坏时逐条跳过并记入 `logs/carrier/brain_config.jsonl`，不会整体失败。

### 5.2 主要方法

| 方法 | 作用 |
|---|---|
| `register(name, config)` | 登记一颗火种；重名返回 `False`，不覆盖。第一颗自动成为当前火种 |
| `unregister(name)` | 注销火种，不自动改选当前火种 |
| `list_brains()` | 按 `(priority, name)` 排序返回 |
| `switch(name)` | 切换当前火种，只改一个内部指针 |
| `fallback(exclude)` | 按优先级选出下一颗可用火种，不切换 |
| `auto_fallback(reason)` | `fallback` 加切换加记录日志，一次完成救场 |
| `mark_unhealthy(name, reason)`、`mark_healthy(name)` | 手工标记健康状态 |
| `health_check(all=False, timeout=3)` | 探测 `/models`；默认只探当前火种 |
| `apply_to_app(brain)` | 把火种写进 `xiaojiao_app` 的 `LLM_BASE`、`LLM_MODEL`、`LLM_KEY` |
| `snapshot()` | 当前状态一览，密钥字段只报"已设置"而不报内容 |

三条设计约束写死在代码里：持久化默认是内存空操作，登记处不会悄悄改写用户的控制文件；
所有探测与写日志都兜住异常，绝不抛出；配置读取采用惰性加载，导入模块不产生磁盘读取。

### 5.3 落盘记录

| 文件 | 内容 |
|---|---|
| `logs/carrier/brain_switch.jsonl` | 换火种历史：时间、来源、目标、原因、是否成功 |
| `logs/carrier/brain_apply.jsonl` | 把火种写入应用全局变量的记录 |
| `logs/carrier/brain_config.jsonl` | 配置读坏时被跳过的条目原文片段 |

## 6. 使用示例

命令行交互（自带的最小操作台）：

```powershell
$env:PYTHONUTF8="1"
python brain_manager.py
```

进入后支持三条命令：`state` 打印各大脑状态，`switch <大脑>` 执行切换，`quit` 退出。

通过监控接口操作：

```bash
curl http://127.0.0.1:5000/api/monitor
curl -X POST http://127.0.0.1:5000/api/monitor/op \
  -H "Content-Type: application/json" -d "{\"op\":\"switch\",\"target\":\"chat\"}"
```

`/api/monitor/op` 支持的 `op` 取值：`switch`、`wake`、`release`、`restart`、`clearWarm`、
`clearVram`、`add`。其中 `clearVram` 会同时调用 ComfyUI 的释放接口与 llama-swap 的卸载接口。

启动时，`start_xiaojiao.py` 的 `start_carrier()` 会扫描能力并注册火种，
打印火种数量与当前火种；只登记一个火种时提示没有备用火种可切。

## 7. "秒级"成立的前提

切换速度取决于底层服务是否支持权重卸载与重新加载，而不是调度代码本身。

| 大脑类型 | 睡眠与唤醒的实现 | 现状 |
|---|---|---|
| 视频与图像（ComfyUI 加 Wan） | 生成完成后保留在内存，聊天大脑上显卡时不终止它；`--lowvram` 把权重放内存 | 已接入 |
| 大语言模型（llama.cpp 与 llama-swap） | 进程常驻，切换等于卸载与加载模型文件，不重启进程 | 已接入，聊天大脑与编码大脑共用 9292 |
| vLLM 与 DeepSeek 等 | vLLM 的睡眠模式 | 未接入。注册表里预留了扩展位置，加进去即可被调度 |

因此准确的说法是：**同一条 llama-swap 内的模型切换是权重的卸载与加载；跨服务的大脑切换
（例如从聊天切到视频）还包含一次进程启动或状态恢复，耗时以秒到分钟计。**
原文档中"秒级"的说法成立范围是前者。

### 7.1 实测：换一次模型到底要多久 —— **瓶颈是磁盘，不是模型、不是调度代码**

同一条 llama-swap 内换模型 = 把几 GB 的 gguf **从磁盘读进显存**。所以耗时几乎完全由**盘的速度**决定：

| 模型文件所在 | 实测顺序读速 | 4.29GB 读进来的理论时间 | 实测首次加载 |
|---|---|---|---|
| `C:`（本机 NVMe） | **1029 MB/s** | 4 秒 | **约 5 秒** |
| `G:`（NVMe 装 USB 硬盘盒，**只跑到 USB 2.0 速度**） | **37 MB/s** | 118 秒 | **120.6 秒** |

· 差 **28 倍**，同样大小的文件。
· 走 llama-swap 那条还要加它自己的健康检查，实测**最长 237 秒**。
· **显存只有一张卡的容量时，每次切换都必须重新读盘**（旧的被卸载、新的装进来），
  所以"换模型慢"是硬件与文件位置的函数，换哪个模型都一样。

**两条能立刻改善的操作**：① 模型放本机盘（或接 USB3 口/换线，37MB/s 明显是没跑到 USB3）；
② `llama-swap.yaml` 里给 `healthCheckTimeout` 一个够大的值 —— 默认 **120 秒**，
实测 DeepSeek-V4-Pro（4.29GB Q8）首载 **120.6 秒**，**被默认值卡在门外**（报 `health check timed out`）。
本项目仓库里的 `llama-swap.yaml` 已设为 **300**。

### 7.2 加一个模型之后，为什么"没生效"

**llama-swap 不会自己重载 yaml**（实测：把新模型写进配置后，它的 `/v1/models` 里仍然没有它）——
**加模型必须重启 llama-swap 进程**。所以"一键加本地 GGUF"这条链的正确顺序是：
写 yaml → 重启 llama-swap → **核实它真的认到了** → 才回报成功。

这一环曾经是坏的（两处：找不到 llama-swap.exe、以及重启命令的 PowerShell 引号转义把配置路径传坏），
表现为**界面说"✅ 已添加"、实际一句都用不了**，甚至把 llama-swap 杀掉却没起来。现在的做法：
从**正在运行的进程**取 exe 路径（毫秒级、一定准），用 `subprocess` + `DETACHED_PROCESS` 启动
（不经过任何 shell），并在重启后轮询 `/v1/models` 最多 20 秒 —— **认到才说成功，没认到就报失败**。

### 7.3 换载期间，探测会失败（正常现象，别误判）

模型加载那 2~4 分钟里，llama-swap 的 HTTP 会卡住甚至重置连接（实测：一条请求在加载中等待
210 秒后成功，同时另一条 `/v1/models` 探测直接失败）。所以**那段时间里任何"这个模型在不在"
的探测都可能失败** —— 载体必须把它当成"正在忙"，而不是"模型不存在"：
· 选择模型时探测失败 → **保留用户选的那个**，不要替换成别的（这个替换逻辑曾经把用户
  静默换到一个坏模型上）；
· 请求本地大脑的超时**必须大于冷启动时间**（现在是 `capabilities.local_timeout_s`，默认 300 秒）；
· 切换模型时**后台预热**，把加载这一步提前吃掉，用户的第一句话就不用等。

## 8. 小脑向量库与大脑标签

小脑的向量库位于 `self_learn/vstore.py`，支持给每条记录打标签，用于记录"从哪条链路学到的"。
代码中实际使用的标签：

| 标签 | 写入位置 | 内容形态 |
|---|---|---|
| `video_prompt` | `video_service/video_api.py` | `用户: <描述> -> 精炼: <提示词>` |
| `tool_skill` | `xiaojiao_app.py` | 工具使用经验 |
| `learned` | `self_learn/learn.py` | 学习到的经验 |
| `reflection` | `self_learn/learn.py` | 反思记录 |

视频链路是最能体现"学以致用"的一条：精炼过的提示词写回向量库，下次遇到相近描述时
先查库命中，直接复用，不再重复调用大脑。原文档中给出的 `chat_answer` 标签在代码里没有出现，
属于示例性质，已按实际标签替换。

## 9. 边界与限制

1. 调度是进程内的。多实例或多进程同时运行时，各自的注册表与锁互不感知。
2. 状态只存在于内存，重启后回到注册表初始值（`SLEEP` 或 `OFF`），不保留上一次的运行状态。
3. `brain_manager._evict_ram_brains()` 已定义但没有任何调用方，`switch_to()` 中已包含等价逻辑，
   属冗余代码。
4. `_start_llama()` 在缺少模型文件时直接返回 `False`，唤醒报告为失败，不写死路径也不给出更多提示；
   排查需要结合配置与环境变量。
5. 火种登记处的探测只做 `GET {base}/models`。端点不支持该路径时，探测会失败，
   即使实际可以对话。
6. 火种登记处的持久化默认不写盘，需要调用方显式传入回调；也就是说，
   通过登记处 "切换当前火种" 默认只在内存中生效。
7. vLLM 睡眠模式与图像大脑（SD3）均为预留扩展，尚未落地。
8. 注册表里的 `vram_gb` 是估算值，不能作为显存规划依据。

## 10. 故障排查

| 现象 | 可能原因 | 排查方式 |
|---|---|---|
| 切换后目标大脑无响应 | 目标服务未启动，或路径配置失效 | 打开 `/monitor` 看状态与任务；确认对应端口在线 |
| 切换很慢 | 目标模型需要从硬盘冷加载 | 看该大脑是否处于温存状态；温存则可秒级切回 |
| 显存没有释放 | 模型仍处于温存，或 `keep_warm` 为真 | 用 `/api/monitor/op` 的 `clearVram` 或 `release` |
| 温存的模型被清掉了 | 切到第三颗大脑时内存单槽策略生效 | 属预期行为；重新切回会触发冷加载 |
| 登记处里火种数为零 | 控制文件没有 `brains`，且旧写法也读不出 | 查看 `logs/carrier/brain_config.jsonl` 的记录 |
| 探测一直失败但对话正常 | 端点不提供 `/models` | 属已知限制，见 9.5 节 |
| 启动提示"只登记了 1 个火种" | 控制文件里只配了一个模型 | 在 `brains` 中至少再配一个作为备用 |
