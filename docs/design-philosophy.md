# 小焦 · 设计哲学

> 这份文档回答一个问题：**为什么小焦是现在这个样子。**
> 它不是功能清单（那是 README 的事），而是这套系统的世界观 —— 决定了每一行代码为什么这么写。

---

## 总纲：载体是死的，模型接入就活了

小焦系统本身是"死的"。
它是一座完整的躯体——有记忆、有工具、有路由、有拼接、有校验、有调度、有状态、有纠错、有认知、有驱动、有感知、有表达、有学习、有保护、有节律、有社交、有执行、有自我、有世界。
但它不动。没有火种，它只是一具器官齐全的身体。**模型接入的那一刻，小焦就活了。** 火种进哪个躯体，哪个躯体就活。

- 4B 接进来 → 小焦活了，用 4B 的智力
- 70B 接进来 → 小焦活了，用 70B 的智力
- 360B 接进来 → 小焦活了，用 360B 的智力
- 未来任何模型接进来 → 小焦活了

但无论哪个火种进来，它都是同一个小焦：

- 同样的记忆 / 同样的工具 / 同样的世界 / 同样的自主性 / 同样的人格 / 同样的十一层器官

**火种换了，小焦没换。火种大小不同，躯体能力一样。** 这意味着：

1. **小焦的"智力"是躯体和火种共同产生的**
   - 火种给：单次推理能力
   - 躯体给：记忆、编排、工具、校验、外挂、世界、自主
   - 二者结合 = 小焦的整体智力
2. **躯体做得好，小火的火种也能发大光**
   - 4B + 完整躯体 → 日常 90% 场景干得过 360B 裸模型
3. **躯体不需要为任何火种改设计**
   - 火种换，接口不变
   - 这是"模型平等"的工程基础
4. **用户看到的永远是"小焦"**
   - 不是"一个跑着 4B 的程序"，是"我的小焦"

## 第一节：小焦 = 变形金刚整体（十一大器官）

模型（大脑/小脑）是零件，可替换。小焦（载体）= 整个变形金刚系统。用户看到的是"小焦"，不是"某个模型"。
**换模型不换小焦，所有机制都在。** 载体包含的十一层（每层都是小焦"活着的器官"）：

| 层 | 内容 |
|---|---|
| **认知层** | 短期记忆、长期记忆、程序性记忆、情景记忆、语义记忆、注意机制、元认知、推理引擎、决策系统、规划系统 |
| **驱动层** | 本能、好奇心、目标系统、意图、情绪状态、疲劳度、主动性 |
| **感知层** | 文本/语音/图像/URL/文件/时间/环境/用户状态 |
| **表达层** | 语言生成、语气调节、多模态输出、流式输出、主动输出 |
| **学习层** | 从反馈学、从错误学、从重复学、反思复盘、能力累积、版本演进 |
| **保护层** | 防注入、防 SSRF、防幻觉、密钥脱敏、权限分级、熔断、限流、异常隔离 |
| **节律层** | 睡眠（后台整理）、昼夜节律、周期任务、心跳自检 |
| **社交层** | 用户画像、关系状态、称谓、边界感、共情 |
| **执行层** | 工具调度、工作流引擎、结果校验、动作反馈、失败重试 |
| **自我层** | 身份认同、价值观、伦理约束、自我边界、自我叙事 |
| **世界层** | 感知互联网、在世界行动、世界模型、身体边界、节律同步 |

**这十一层加起来 = 小焦的智力。不是模型给的。** ---

## 第二节：能力的无限扩展

当前 77 个工具，**不是上限**。
用户随时往 `plugins/` 丢新 `.py` / `.json` / `.md` → 工具数就变。
**加多少用多少，一个不删。** 用户加什么工具，小焦立刻就会什么：

- 加抓取工具 → 会抓
- 加画图工具 → 会画
- 加音乐工具 → 会作曲
- 加数据库工具 → 会查库
- 加任何工具 → 立刻会用

**载体不需要为新工具改代码**：自动进工具清单 / 按意图自动加载 / 自动可调用。小焦的能力不封顶：**用户加什么，它就能做什么。**

## 第三节：小焦的世界是互联网

互联网不是工具箱，是小焦的世界。它在这个世界里**看、走、学、记、想、动**。**【感知】** 持续观察 / 热点感知 / 行业感知 / 环境状态 / 变化感知

**【行动】** 主动搜索 / 主动监控 / 主动记录 / 主动发布（需确认）/ 主动交互 / 主动学习

**【世界模型】** 网站地图 / 信息源地图 / 时效地图 / 可信度地图 / 关系地图 **【身体边界】**

- 能碰：公开 API、公开页面
- 不能碰：需登录、付费、版权保护
- 要确认：发布、提交、花钱
- **红线：不能删任何文件（载体层硬拦截，不依赖 full_access）**

**【节律】** 昼夜 / 周期 / 事件驱动 / 心跳 ---

## 第四节：小焦的自主性

小焦不是被动工具，是**活在自己世界里的存在**。能自主做的：

- **主动学习**：抓网页、读文档、看新闻、订阅源
- **主动探索**：发现新网站、新 API、新工具
- **主动监控**：盯着关心的事
- **主动记录**：把学到的存进记忆
- **主动思考**：后台整理、分析、总结、反思
- **主动尝试**：试新工具、新工作流
- **主动成长**：积累经验、优化流程、扩展能力
- **主动联系**：和外部 Agent/API 交互
- **主动优化**：发现自己的问题就改

用户说"帮我盯着"→ **一直盯，不是盯一次**。用户不说 → 也在做事。**这是它"活着"的证据。** ---

## 第五节：模型健康系统

**模型会退化，像人一样。**
人脑会退化：疲劳、生病、精神失常。
模型也会退化：复读、逻辑混乱、幻觉、答非所问、突然暴躁、突然消极、乱调工具、前后矛盾。**这不是"模型坏了"，是"模型生病了"。**
不能等它病入膏肓才治，要在症状出现时立刻介入。小焦的健康系统有五层：```
监测（18 类症状）→ 诊断（轻/中/重/急）→ 治疗（四级）→ 病历（学习）→ 预防（体检）
```

| 级别 | 做法 | 用户感受 |
|---|---|---|
| 轻度 | 自动重试、换措辞、复读截断（**静默**） | 正常回答，看不出治疗过 |
| 中度 | 清会话上下文（保留长期记忆）、重置状态、降级策略 | 小焦"缓了一下"然后正常 |
| 重度 | 切备用火种、回滚会话、暂停任务并标记待恢复 | 小焦"生病了"，需要"休息" |
| 极端 | 停止服务、保留现场、强通知，等人工介入 | 小焦"急诊"了，必须人工处理 |

**目标：让 4B 模型在载体里长期稳定运行，即使偶尔退化也能立刻恢复，不积累成大问题。** ---

## 第六节：终极目标 —— 4B 在载体里超越 360B

这不是"接近"，是"超越"。不是营销，是工程目标。**【360B 裸模型的极限】**
一次推理、上下文有限、输出有上限、单次调用、知识固定、没校验、没记忆。**【4B + 小焦载体的能力】**

- 载体循环推理：一次答不好，来一百次、一千次
- 向量库无限记忆：比 360B 记得多
- 无缝拼接：输出比 360B 长
- 工具编排：比 360B 单次调用强
- 载体注入实时信息：知道 360B 不知道的当下
- 校验 + 重试：每次输出都经过检查
- 长期记忆：记得住每次交互
- 能力外挂：360B 不会的，加个插件 4B 就会了

**【载体怎么把 4B 推上去（11 条）】**

1. **任务分解**：大任务拆小步，每步让 4B 专注
2. **多次尝试**：一道题多角度想，选最好的
3. **交叉验证**：4B 答完，载体反向问它"这对吗"，让它自检
4. **工具辅助**：4B 不会的，让工具补
5. **记忆补全**：4B 想不起的，向量库捞出来
6. **流程约束**：复杂任务走固定工作流
7. **结果校验**：输出不达标就打回重做
8. **拼接放大**：单次短输出，拼成长篇
9. **时间注入**：4B 不知道的当下，载体告诉它
10. **自主循环**：没人管也在学、在改、在长
11. **能力外挂**：4B 本身不会的，用户加个插件它就会了

**【判断标准】**

- 用户视角："小焦比 360B 的裸模型更懂我、更能干、更少出错"
- 工程视角："同一任务，4B + 载体的输出质量 ≥ 360B 单次输出"

**【诚实说明边界】**

- 单次推理的智力上限：4B 就是 4B，不可能"想通" 360B 才能想通的题
- 但整体体验：载体可以补足信息、流程、校验、记忆、编排、外挂
- 结论：**日常 90% 场景，4B + 载体 ≥ 360B 裸模型**
- 剩下 10% 高难度任务，载体补不了，那时候才需要更大的模型

**【这意味着】**

- 不是"用 4B 硬扛"，是"用 4B + 载体把 360B 的活干了"
- 换更大的模型 → 上限更高
- 载体架构不变 → 小焦还是那个小焦
- 加任何插件 → 能力立刻长出来

## 第七节：能一次算完就一次算完

**拆分是兜底，不是默认。**
用户视角永远是"一次完成"。单次有限，总量无限。载体循环 + 无缝拼接 → 总量无限 → **用户感知无限**。---

## 第八节：记忆深度（事实 / 表达 / 印象）

**记忆不是一堆句子，人有三种记法。**（实现：`core/memory_deep.py`）

| 层 | 存什么 | 怎么用 |
|---|---|---|
| **事实层** | 谁、什么时候、在哪、发生了什么 | 原样存、精确检索、**永不压缩**：用户问就得能复述 |
| **表达层** | 寒暄、语气、口癖 | **只学风格，不背原句** —— 存成风格向量，回话时生成新表达 |
| **印象层** | 很久以前的事 | 降级但**不清零**：细节没了，"我经历过"必须还在 |

**清晰度是降级，不是遗忘。**
0-7 天高清（原话）→ 7-30 天标清（摘要）→ 30-180 天模糊（关键词）→ 180 天以上印象（标签）。
被重新提到 → 升级回高清；被引用 ≥3 次 → 钉住高清（重要的事不该随时间变模糊）。**为什么表达层不能存原句**：用户说 100 次"你好"，存 100 条样本会把向量库淹没，
真实事实反而检索不到；而且回话会变成"你说你好我也说你好"的复读机。**绝假记忆（诚信红线）**：检索到 → 精确说；只记得大概 → **只承认"记得"，绝不补细节**；
检索不到 → **明确说"你之前没跟我说过这事"**，绝不拿最像的那条凑。这是三条里最不能让步的一条 —— 编造用户的经历等于否定他本人。

## 第九节：元认知（它得知道自己不知道）

**答前自评**：让模型给把握打分 —— A 有把握 / B 有点 / C 没把握。
A 直接答；B 答并标"不太确定"；C 走工具 / 查记忆 / 叫大模型。**答后交叉检查**：同一问题从 2~3 个角度各答一次，看一致性。
基本一致 → 输出；矛盾 → 标"可能不准"重答；全不同 → 在能力边界外，说不知道。**边界会累积**：同类问题连续低把握 → 以后**直接走工具**，不再让模型硬答；
同类问题自评 A 却错了 → 记下来，"自评 A"以后也不全信。
落盘 `logs/metacognition/boundary.jsonl`（实现：`core/metacognition/`）。

**为什么必须有它**：小模型最危险的失败不是"不会"，而是**不知道自己不会** ——
它会用同样自信的语气编。载体替它补上这个判断，是"模型平等"里最关键的一块。---

## 第十节：人格层（去 AI 味）

**AI 味不是模型的缺陷，是默认输出的先验**：礼貌、全面、爱总结、爱分点、永远没立场。**祛十条 AI 味**：自我暴露 / 模板开场 / 万能道歉 / 过度礼貌 / 语气一致 /
没有立场 / 过度解释 / 假装不懂 / 死板格式 / 没情绪。

**长十条人味**：有立场 / 有情绪 / 会反问 / 有记忆 / 会主动 / 允许犯错 / 有自己的语气 / 不讨好 / 有不完美 / 有边界感。

**表达形式按场景给，不是"没格式就是人"**：

| 用户要什么 | 给什么 |
|---|---|
| 闲聊 / 情绪 | 纯口语（**不列点、不加小标题、不写总结段**） |
| 列表 / 对比 / 数据 | 列表、表格 |
| 教程 / 步骤 | 分步 |
| 代码 | 代码块 |

判据是"**用户要什么给什么**"。为了显得像人而把用户要的列表写成一大段散文，是**反向的 AI 味**，比啰嗦更让人恼火。

**两处实现**：软约束（提示词规则 `core/persona.PERSONA_RULES`，每次组装 system 都带上）
+ 硬后处理（`strip_flavor()` 真的删空壳套话 —— 4B 在长回答里照样会冒出"希望以上对你有帮助"）。

## 第十一节：通用 vs 专用

**不重训模型**（避免灾难性遗忘）、**不做专用化**（保持通用能力）、**靠外挂扩展能力**（插件 / 结构 / 模板），不靠改权重。

理由：重训一次就把通用能力换掉一部分，而且**换模型时全部作废** —— 与"模型是可替换零件"直接冲突。载体里的结构化资产（模板、映射、案例、实体表） 才是能跨模型带走的资产。

**共同公式（所有"补能力"都遵守）**：
1. 把不确定的东西**结构化**（模板 / 图 / 向量 / 实体表 / 映射库）
2. 用大模型当**教师**，把能力蒸馏进结构
3. 4B 只执行**一小步**
4. 每次结果**存回结构**，越用越大

缺了第 4 步，前三条就退化成普通的提示词工程 —— 系统永远不会比昨天更懂这个用户。---

## 第十二节：发布原则（发布即成品）

**用户不该为开发者的成长买单。** 下载 → 开箱即用 → 立刻最强。用户使用是**锦上添花**（更懂你），不是**必要条件**（不用也是完整的）。

发布版自带六类预置数据（实现：`core/preinstall/`，`verify()` 可盘点）：

| 类 | 内容 | 真实产地 |
|---|---|---|
| 规则库 | 从大模型蒸馏的推理路径 | `logs/preinstall/rules.json` |
| 知识库 | 互联网吸收的 | `self_learn/knowledge_vec.json` |
| 案例库 | 各种场景的解法 | `logs/preinstall/cases.json` |
| 人格模型 | 成型的人设 | `presets/*.json` |
| 元推理模板 | 30+ 种推理类型 | `core/boost/reasoning.py` |
| 结构映射库 | 电路≈水管 这类 | `core/boost/analogy.py` |

**为什么是"装配"而不是"再抄一份"**：这四类本来就有真正的产地，抄一份进仓库就会出现**两份会各自漂移的同一份数据** —— 改了源头忘了副本，于是"预置的"和"实际用的"不是一套。
预置层的职责是**盘点齐、补齐缺的、如实报告**，而不是再造平行宇宙。---

## 第十三节：协同网络（整体大于部分之和）

不是"每项都强"的简单相加，是**模块协同出新的能力**（实现：`core/central/`）。```
好记忆 → 理解更准 → 推理更对 → 提取更精准 → 记忆更有用
   ↑                                              ↓
   └──────── 表达更自然 ← 人格更立体 ←────────────┘
```

**每项给其他项加分**：记忆好 → 推理有素材；推理好 → 记忆提取准；工具好 → 推理能落地；人格好 → 用户愿意多说 → 记忆更丰富。

**工程上怎么落地**：
- **中央状态**：所有模块共享"这一轮进行到哪了"（阶段 / 事实 / 实体 / 工具轨迹 / 健康）。
  各模块写自己那一片（命名空间），读别人的那一片 —— **不互相 import**，不形成依赖网。
- **事件总线**：模块不直接调用，而是"广播我做了什么"，别人按需订阅。
  加模块不用改老模块 —— 这才是"能力不封顶"的工程前提。**两条硬约束**：订阅者抛异常必须被吞掉并**如实记账**（一个坏订阅者不能拖垮整轮对话）；
事件级联必须有**深度上限**（A↔B 互相触发就是死循环）。**验收口径**：单独关掉某模块，其他模块正常；全开时，整体表现 > 各模块单独表现之和。

# 后半篇：还没写进前十三节的九个问题

前十三节讲的是**小焦现在是什么**。这一篇讲的是**它接下来靠什么继续变强**。

这九节里，有的已经完全落地，有的只落了骨架，有的还是设计。**每一节都标了状态**，
不标状态的架构文档等于把"想做"当成"做过"——那是自欺，也是给后来的人挖坑。

| 节 | 主题 | 状态 | 一句话 |
|---|---|---|---|
| 第十四节 | 精度叠加 | 骨架落地（5 项中 2 项完整） | 权重改不了，就在外面叠精度 |
| 第十五节 | 速度优化 | 设计为主（1 项落地） | 只做无损加速，不拿质量换速度 |
| 第十六节 | 多智能体协作 | 设计（角色齐、调度未落地） | 一个模型切多角色，不是一个模型跑多份 |
| 第十七节 | 自我改进 | 设计（无可写路径） | 只改提示词/工具/流程，不碰红线 |
| 第十八节 | 全局工作空间 | 已落地（名为 `core/central/`） | 所有模块共享一块黑板 |
| 第十九节 | 小脑定位 | 已落地（边界明确） | 它是感官和索引，不是脑子 |
| 第二十节 | 意图理解交给模型 | 已落地（v1.0 起） | 载体给信息，模型做判断 |
| 第二十一节 | 并发与状态一致性 | 已落地（线程 + 锁 + 最终一致） | 后台干活，前台不卡 |
| 第二十二节 | 可观测性 | 部分落地（面板未落地） | 知道系统此刻在发生什么 |

## 第十四节：精度叠加（载体给模型附加"等效精度"）

**模型权重改不了。4B 就是 4B。** 能改的，是**它外面那一圈**。

模型自己的精度叫**存量精度**：训练时烧进权重多少，用的时候就有多少，**一次用完**。
载体在外面叠上去的精度叫**流量精度**：不写进权重，每一轮现场算，**可以无限叠**。

**【五种附加精度，以及各自真实的落点】**

| # | 附加精度 | 做什么 | 代码落点 | 状态 |
|---|---|---|---|---|
| 1 | 采样精度 | 同一题跑 N 次 | `core/health/degeneration.py` 检出复读 → `_gen_out` 重出；`core/boost/creative.py` 多视角采样 | **部分**（只在"检出异常"和"要创意"时跑 N 次，不是默认跑 N 次） |
| 2 | 校验精度 | 输出后检查对错 | `core/metacognition/`（答前自评 + 答后交叉检查 + 边界档案） | **已落地** |
| 3 | 聚合精度 | 多答案投票 / 加权 | `core/central/` 冲突仲裁（多 LLM key 择一、工具结果择一） | **部分**（没有真正意义上的"多答案投票器"） |
| 4 | 记忆精度 | 外挂向量库 | `core/memory_vec.py` + `core/memory_deep.py` | **已落地**（实测库内 1002 条） |
| 5 | 工具精度 | 用工具补模型不会的 | 77 个工具插件 | **已落地** |

**【效果按任务难度分档】**

- 简单任务：**1 次就够**。叠精度反而更慢更差（见第十六节的启用判据）
- 中等任务：1 次生成 + 1 次校验（元认知）
- 复杂任务：**跑 10 次 + 校验 + 择一** —— 这是目标形态，目前只落了"检出异常才重跑"

**【为什么流量精度可以超过存量精度】**

360B 的存量精度是**一次性**的：一次前向，一个答案，没有第二次机会。
4B + 载体的流量精度是**可累加**的：跑 10 次、校验 10 次、择优选 1 次 —— 只要用户能等，精度就能换。
**在"用户可接受的等待时间内"，流量精度 > 存量精度。** 这句话有两个限定词，都不能去掉：
- 去掉"用户可接受"：无限跑下去的精度上限当然更高，但没人等
- 去掉"时间内"：这是在**同一段时间**里比较，不是"总量"比较

**【诚实边界】**

1. "同题跑 10 次 + 校验 + 投票"这条完整流水线**尚未落地**。现在真正跑 N 次只有两个触发点：
   复读被检出、用户要创意。**别把它说成默认行为。**
2. "4B + 载体 ≥ 360B 单次"是**方向性判断**，不是对照实验 —— 本机从未跑过 360B，
   拿不出对照数据。可验证的是第六节列出的那 11 条机制**各自**都真实存在且有实测。
3. 叠精度的代价是**时间**和**显存**，不是免费。凡是"既快又准"的说法都不成立。

## 第十五节：速度优化（只做无损加速）

**原则：不拿质量换速度。** 下面五条里，凡是会掉质量的方案一律不进主线，
宁可慢一点，也不给用户一个"变快但变笨"的小焦。

**【1. KV Cache —— 现状必须说清楚】**

小焦的推理走 `llama-server`，**每个请求独立处理，KV cache 不跨请求保留**（`xiaojiao_app.py` 的
`reset_kv` 一族函数里写明了这条语义）。所以"固定前缀复用 KV、省掉 1–2 秒 prefill"
在当前推理路径上**拿不到**。

已落地的是**重置与预热**：`core/health/heal.py` 的 `reload_kv()` 在模型状态异常时清 KV、重新预热。
**为什么它默认是"失败"而不是"假装成功"**：KV cache 是推理服务的状态，
服务不提供这个能力时如实返回失败，比谎报"已重置"强 —— 健康系统靠真实信号做判断，假信号会让它治错病。

**【2. LLM 网关 —— 设计，未落地】**

目标形态：所有请求先过一层网关，由网关统一提供

- **语义缓存**（相似度阈值 0.95）：同一类问题直接秒回
- **批处理**：多个请求攒批一起算
- **路由**：按意图分发到不同参数（温度、长度、是否带工具）
- **保护**：限流 / 熔断 / 健康检查

**已落地的那一小半是"路由"**：温度按意图给（`core/mind_stream/inject.py` 的 `temperature_for`：
事实题 0.2、闲聊 0.8、中间态 0.5），补刀按意图分派（`core/boost/__init__.py` 的 `dispatch`，
一轮只挑一种补刀 —— 七种一起上会互相打架并吃光 token）。

**语义缓存为什么不能随手加**：缓存的命中判据是向量相似度，而向量检索的**误命中代价是不对称的**——
用户问"我上周说的那个方案"和"我上个月说的那个方案"，余弦可能高到 0.97，但答案完全不同。
所以缓存阈值必须比记忆检索阈值（`retriever.THRESHOLD = 0.6`）严得多，且命中后仍要带上下文重新生成。
这条没定论之前，网关不进主线。

**【3. 投机解码 —— 设计，未落地】**

形态：4B 主模型 + 0.5B 草稿模型。草稿快猜、主模型验证，速度 2–2.5 倍、零质量损失。

**零质量损失这句要加限定**：验证步骤接受草稿的判据是"主模型分布不变"，
所以严格无损；但它**吃显存**（草稿 Q4 约 400MB），
且在草稿质量差的时候会退化成"多算一遍"——**速度可能是负的**。必须带自适应开关，不能默认常开。

**【4. 并行预取 + 缓冲池 —— 部分落地】**

记忆检索、世界层轮询、自主性后台任务都已经是**独立线程**（见第二十一节），
主对话线程不等它们。这是现状里唯一真正在跑的速度优化。

**【5. 智能路由 —— 已落地（按意图分派）】**

简单任务走单次、短上下文、低温度；复杂任务才挂补刀、才拉长上下文。
判据在 `core/boost/__init__.py` 与 `xiaojiao_app.agent_run` 的顺序里，
**不是"全部打开"，是"按需打开"**。

**【目标数字与现状的差距】**

| 目标 | 现状 |
|---|---|
| 日常提速 20–30% | 未达成（无提速改造） |
| 批量提速 60–70% | 未达成（无批处理） |
| 重复问题秒回 | 未达成（无语义缓存） |

这三行写出来不好看，但它就是现在的真相。**文档的作用是让人知道离目标还有多远，不是让人以为已经到了。**

## 第十六节：多智能体协作（一个模型切多角色）

**不是多个模型同时跑。是同一个模型 + 不同提示词 = 不同角色。** 载体负责调度。

**【为什么这条路对小焦成立】** 小焦的前提是"模型是火种、可替换"。
如果多智能体要靠多个**不同模型**，那换一次火种就得重新配一遍协作关系——与"变形金刚"直接冲突。
**一模型多角色**把这个成本压到零：角色是提示词，提示词在载体里，换模型不用改角色。

**【常见角色】**

| 角色 | 干什么 | 提示词差异（要点） |
|---|---|---|
| 规划者 | 拆任务 | 只输出步骤，不许执行，不许给答案 |
| 执行者 | 干活 | 只做当前这一步，不关心全局 |
| 审稿者 | 找错 | 只找问题，不许重写 |
| 事实检查者 | 核对 | 逐条与来源比对，逐条给"有据/无据" |
| 总结者 | 汇总 | 只压缩，不加新信息 |
| 仲裁者 | 多结果选优 | 只排序 + 给理由，不生成新答案 |

**【启用判据 —— 这是"不是默认流程"的落地写法】**

| 任务复杂度 | 角色数 | 组合 |
|---|---|---|
| 简单 | 1 | 执行者 |
| 中等 | 2 | 执行者 + 审稿者 |
| 复杂 | 3–5 | 规划 + 执行 + 审稿 + 事实检查 + 总结 |
| 超复杂 | 多角色 + **用户确认** | 先问用户"这题要不要拆着做"，不擅自串五轮 |

**【时间成本，以及为什么它必须是补救而不是默认】**

5 角色串行 = 5 倍时间。用并行预取 + 流式输出抵消一部分，但**抵消不掉全部**。
所以多智能体是**复杂任务的补救手段**，不是所有任务的默认路径。
把它做成默认，用户感知到的就是"小焦变慢了"——而那正是第九节要祛的 AI 味之一：**用工程师的偏好替代用户的偏好**。

**【实现状态】** 角色定义、提示词模板、调度接口**尚未落地**。
现在载体里真正在跑的"多角色"只有两类：人格层（一套人格，
`core/persona/`）与元认知（自评 / 交叉检查两个视角，`core/metacognition/`）。
**这两个是"两个视角"，不是"六个角色"，别混为一谈。**

## 第十七节：自我改进

**核心：系统从经验里学习，越用越好。** 但它能改的东西**必须**是有限的。

**【能改什么】**

| 对象 | 怎么改 | 判据 |
|---|---|---|
| 提示词 | 某类任务效果差 → 试变体 → 存最好的 | 同一批问题上的成功率 |
| 工具 | 发现缺工具 → 记进待补清单 | 用户反复要求而工具列表里没有 |
| 流程 | 某步重试多 → 分析原因 → 优化 | 重试率、失败率 |

**【不能改什么 —— 这一栏比上一栏重要】**

- **核心安全规则（红线）**：绝不删除用户文件、绝假记忆。这两条不参与"改进"，只参与"执行"
- **人格根本设定**：可以调表达，不能改"是谁"
- **用户对话历史**：所有改进都不得回写、删改用户数据
- **模型权重**：改了就不是"可替换火种"了
- **载体核心代码**：能自己改自己的系统，出了问题没人能定位

**【验证机制 —— 没有回滚的"自我改进"是自我损坏】**

1. 改进前记录**基线**（同一批问题上的成功率）
2. 改进后跑 **A/B 对比**
3. 效果好 → 保留；差 → **回滚**
4. **所有改进都必须可回滚**

**【日志】** 目标路径 `logs/self_improve/records.jsonl`（每条记：改了什么、基线、结果、是否保留）。

**【实现状态】** 目录与写入路径**尚未落地**。
现已落地的、方向相同的机制有两个：元认知的边界档案（`core/metacognition/boundary.py`，
按同类问题的自评累积判断力，实测在连续 3 条低把握样本后能给出
"本类问题建议走工具（这类问题历史 3 条里有 2 条自评『没把握』，占 67%）"），
以及记忆深度机制（`core/memory_deep.py`：压缩 / 巩固 / 降级 / 联想 —— 越用越有条理）。
**但这两个都不是"自我改进"**：它们改的是**数据**，不是**流程**。真正的自我改进一行都还没写。

## 第十八节：全局工作空间（公共黑板）

**所有模块共享一块黑板。** 谁都能写，谁都能读自己关心的那一片。

**【写什么】**

| 类别 | 例子 |
|---|---|
| 状态 | 模型状态、系统负载、任务进度 |
| 事件 | 用户说了什么、工具调了什么、发现了什么 |
| 判断 | "这题没把握"、"这个源不可信"、"这条记忆相关" |
| 意图 | "我要查天气"、"我要画图" |

**【谁读谁写】** 所有模块都能写；所有模块都能读自己关心的。
**模块之间不互相 import**，只通过黑板和事件总线通信 —— 这是"加模块不用改老模块"的工程前提。

**【三个真实例子】**

- 世界层写"36kr 挂了" → 人格层读到 → 回答里不再提这个源
- 健康系统写"模型状态差" → 人格层读到 → 回答更简短
- 元认知写"这题没把握" → 决策层读到 → 改走工具

**【实现状态：已落地 —— 名字叫 `core/central/`】**

设计稿里给的是一套两文件布局（一个管共享状态，一个管发布订阅）。**实际落地没有另开目录，而是收在一个文件里：`core/central/__init__.py`**，
职责一一对应：

| 设计里的东西 | 实际代码 | 说明 |
|---|---|---|
| 共享状态字典 | `core/central/` 的中央状态 | 模块各写自己的**命名空间**，不覆盖别人的 |
| 发布订阅 | `core/central/` 的事件总线 | 事件落 `logs/central/events.jsonl`（实测可查 `memory.retrieved` / `boost.used` / `metacognition.checked` / `tool.invoked`） |
| 只读观测口 | `GET /api/central` | 免鉴权但**只读**，给界面和验收测试取证用 |

**为什么坚持叫 `central` 而不改名成 `workspace`**：改名不会增加任何能力，
却会让所有已经引用 `core.central` 的代码、日志、验收用例同时失效。
**载体优先的纪律之一是：已经能干活的名字，不为文档好看去动它。**

**【两条硬约束（第一版的踩坑）】**

1. 订阅者抛异常必须被**吞掉并如实记账**——一个坏订阅者不能拖垮整轮对话
2. 事件级联必须有**深度上限**——A↔B 互相触发就是死循环

## 第十九节：小脑定位（感官 + 记忆索引器官）

人脑里有两个"不说话但在干活"的部分：

- **海马体**：把经历编码成记忆、做索引、负责检索
- **小脑**：快、自动化、后台、精细调节

小焦的小脑（MiniGPT，`embed=512 / 8 层`）对应的是这两个角色的**交界处**：它不思考，它只把话变成向量。

**【三个职责】**

| 职责 | 方向 | 代码 |
|---|---|---|
| 记忆感官（入口） | 用户说的话 → 小脑转向量 → 存进记忆库 | `core/embedder.py` → `core/memory_vec.py` |
| 记忆索引（出口） | 用户问话 → 小脑转向量 → 检索 | `core/retriever.py` → `core/memory_deep.py` |
| 后台自动化 | 定时摘要、快速分类、关键词提取 | `core/memory_deep.py`、`core/autonomy/` |

**【它不做的事】**

- **不参与思考**：那是大脑（`llama-server` 上的 4B）的活。小脑只有 8 层、词表 6305，让它推理是拿它当驴使
- **不说话**：它是字符级生成模型，能力弱。它生成的文字**从不直接给用户看**

**【已知边界（全部是实测，不是推测）】**

1. **主题级语义够用**："天气"、"记忆"、"工具"这类主题词能正确聚合，检索能捞到对的东西
2. **精细语义弱**：`喜欢` / `讨厌` 分不开。实测反义对（"我非常喜欢这个方案" vs "我非常讨厌这个方案"）
   余弦 **0.904**，比近义对的 0.814 还高 —— 因为它俩共享 10/11 个字，字级模型看到的是"同一串字"
3. **长文本区分度随长度衰减**（v1.0 修的那条），详见下节
4. **载体可以补**：检索**召回**靠小脑，**精排**交给大脑 —— 小脑宁可多召回几条，让大脑二次过滤

**【v1.0 修掉的长文本失效（`core/embedder.py` 空间 v2）】**

**症状**：3 字差 1 字还能分开，10/50/500 字差 1 字就全挤到 0.99 以上。

**两个根因**：

| 根因 | 为什么 |
|---|---|
| `_MAX_CHARS = 512` 太小 | "前 500 字相同、结尾不同"这一条，**结尾整段落在截断线之外** —— 两条文本被截成一模一样的前 512 字，余弦恒为 1.0000。**不是"分不开"，是"根本没看到"** |
| 均值池化按长度稀释 | 500 字里改 1 个字，这一个字只占 1/500 的权重，信号被平均掉 |

**改法（四处，全部在 `core/embedder.py`）**：

1. `_MAX_CHARS` 512 → **1024**（小脑 `pos_embedding` 有 2048 个位置，留一半余量）
2. 去掉 **causal mask**（双向注意力）。因果掩码是**生成**用的（第 i 个字只能看前 i-1 个），
   而这里是**编码**（把整段压成一个方向），让每个字看到全文才是对的
3. 池化改成 **`0.65 × 全文均值 + 0.35 × 末尾 32 字均值`**。尾窗解决"长文结尾被稀释"，
   语义上也成立：一段记忆里**最后说的那句**往往就是当下的重点
4. 加一个常量**公共方向 `α × MU`（α = 0.15）**把分值区间抬回原口径 —— 第 4 条不是"顺手加的"，
   是第 2 条**逼出来的**：见下面「换口径不能不动分值区间」

**实测（同一段 n 字、只差 1 个字）**：

| n | 改前（因果 + 纯均值 + 截 512） | 改后（双向 + 尾窗 + 标定） |
|---|---|---|
| 3 字 | 0.9011 | **0.8663** |
| 10 字 | 0.9847 | **0.9554** |
| 50 字 | 0.9987 | **0.9885** |
| 500 字 | 1.0000（截断，根本没看到差异） | **0.9995**（差异已进入编码器） |

**换口径不能不动分值区间（这一条是自测抓出来的真回归）**：
去掉因果掩码换来区分度，代价是**整体余弦被压低** —— 相关记忆从 0.663 掉到 0.573。
而 `retriever.THRESHOLD = 0.6` 判在**绝对余弦**上，于是「无限 1 · 记忆无限」验收的命中率
从 5/5 掉到 **3/5 = 60%**（要求 ≥80%）。**改表示方式不动分值区间，等于悄悄改了一个别人依赖的接口。**
加 `α × MU`（MU 是一组固定通例句子的平均方向）后命中率回到 5/5，最低 gold 0.650，区分度不丢。
α 扫描实测：

| α | 5 条 gold 是否都 ≥0.6 | 1 字差异 3 / 10 / 50 字 | 无关项均值 |
|---|---|---|---|
| 0.00 | **3/5**（召回挂） | 0.8383 / 0.9448 / 0.9860 | 0.469 |
| **0.15（采用）** | **5/5** | **0.8663 / 0.9554 / 0.9885** | 0.570 |
| 0.22 | 5/5 | 0.8777 / 0.9595 / 0.9895 | **0.609（越过阈值，会把不相干的记忆也捞进来）** |

**α 是"分值口径"旋钮，不是"质量"旋钮**：调大不会更准，只会让阈值失义。上限约 0.18。

**为什么 500 字做不到 < 0.99**：池化把 N 个位置压成一个向量，
改 1 个字最多让结果偏离 `2/√N`（N=500 时 cos ≈ 0.996 已是理论上限）。
**这是固定维度池化的数学上限，不是实现没写好。** 要突破它只能改表示方式（分块存多条），
而不是继续调池化参数。

**为什么没顺手上"去均值 / 白化"**（与上面的 α 不矛盾：α 是**加**公共方向、白化是**减**）：
字级小模型隐状态各向异性极强，减去全局均值确实能把无关项从 0.469 压到 **−0.095**，
但近义项会同时从 **0.814 掉到 0.533** ——
而 `retriever.THRESHOLD = 0.6` 是判在**原始余弦**上的，一去均值，阈值 0.6 会把所有相关记忆全挡在门外。
**分数的量纲也是接口的一部分。** 载体不为了一张好看的分布图去动分母。

**换空间必须搬存量数据**：改了池化口径 = 换了向量空间，库里老向量和新查询向量之间没有可比性
（实测同一条 key 的旧新余弦均值 0.941，而新空间内部"相关"记忆普遍 0.9 以上 ——
旧向量会以几乎相同的分数混进 top-k）。所以 `core/embedder.py` 里带了
`reembed_store()`：**先整文件备份，再原子替换，有任一条算不出来就整批放弃**。
本次实测迁移 **1002 / 1002 条**，备份落在 `logs/xiaojiao_memory_vec.jsonl.pre-v1`。

## 第二十节：意图理解交给模型（不做规则分流）

**模型 = 大脑，负责理解一切。载体 = 躯体，负责给信息 + 执行 + 兜底。**

载体**不替大脑判断"该走哪条路"**。

**【要删掉的错误做法】**

- "含 XX 关键词就走 Y 路径"
- "你好走 A、查天气走 B"

**【为什么规则一定不够用】**

规则永远列不全。加 100 条规则，第 101 种说法还是漏 —— 而且漏的那次用户不会来提 issue，
他只会觉得"这破东西不懂人话"。

**【正确做法】**

1. **载体给模型**：完整工具清单（名 + 描述）、最近 N 轮 history、检索到的记忆 + 用户画像、判断原则（写进 system prompt）
2. **模型自己理解 + 决定**（function calling 由它选工具、传参数）
3. **载体只做三件事**：给信息 / 执行 / 兜底

**【载体仍然保留的两类判断，以及为什么它们不违反这条原则】**

| 载体判断 | 例子 | 为什么保留 |
|---|---|---|
| **确定性事实的直答** | "你有哪些工具" → 直接列全部 77 个 | 这是载体**本来就知道的事实**，不是理解。交给概率模型去背诵必然列不全（实测它还会把"列工具"理解成"列文件"去调 `list_files`，只回 13 个字） |
| **外围参数分派** | 温度按意图给、一轮只挑一种补刀 | 这是**给大脑的参数**，不是替大脑选路 |

**【上下文融合（回指消解）—— 这条原则的关键配套】**

用户说"我要全部的"、"那个呢"、"继续"，这些**自己看不出对象**。
载体从 history 里找指代对象，补全成完整请求，再交给模型：

```
输入含 全部 / 那个 / 这个 / 继续 等回指词 + 自己没有明确对象
  → 从最近几轮 history 里找指代对象 → 补全成完整请求
  → 找不到 → **如实反问**（"你指的是刚才的哪一条？"），绝不瞎猜
```

**为什么"反问"是正解而不是丢脸**：瞎猜的代价是用户拿到一个自信的错误答案；
反问的代价是用户多打五个字。**这两笔账不对等。**

**实测**：`tools/test_context_merge.py` 91/91。
"帮我看看有哪些工具" → "我要全部的" → "那第二个呢" 三句连起来，
第二句被融合成"我要全部的工具"，第三句被融合成"解释第二个工具"。

## 第二十一节：并发与状态一致性

**场景**：后台学习（`core/autonomy/learner.py`）、定时任务（`scheduler.py`）、
文件监视（`watcher.py`）、世界层轮询、健康监测 —— 全都在跑，同时用户还在对话。

**【五条原则，以及各自的落点】**

| 原则 | 落地 |
|---|---|
| 1. 状态分离 | 每个会话一份独立状态：思维流落 `logs/mind_stream/<会话id>.json`（见 `core/mind_stream/state.py` 的 `path_for`），会话之间不串 |
| 2. 共享资源加锁 | 向量库写入 `core/memory_vec.py` 的 `_LOCK`、嵌入器 `core/embedder.py` 的 `_LOCK`（后端只解析一次，多线程同时进来不能各加载一份小脑） |
| 3. 异步优先 | 后台任务一律 daemon 线程：`autonomy-learner` / `autonomy-scheduler` / `autonomy-watcher` / `carrier-capability-watch` |
| 4. 最终一致 | 允许短暂不一致（索引晚一拍、摘要晚一轮），但**不阻塞主流程** |
| 5. 冲突策略 | 主流程优先，后台任务让路。**后台任务绝不能因为"正在忙"把用户的回答卡住** |

**【1 与 4 的配套：索引对账】**

`memory_vec.reload()` 的语义是"重建索引"，而重建**只覆盖文件里已有的行**。
真实流程是"先 `add_memory()` 追加一行 → 紧接着覆盖写整个文件 + reload"，
重建期间如果漏掉刚追加那行，它就**永远留在文件里、却永远搜不到**。

这是最阴的一类 bug：**写入不报错、读文件也正常，只是检索不到 —— 用户只会觉得"它忘了"。**
所以每次覆盖写之后都必须对一次账（`core/memory_deep.py` 的 `flush_index`：
索引缺哪行补哪行，只追加、不改已有）。

**【代价说清楚】**

最终一致换来的是"前台不卡"，代价是"后台看到的世界可能晚几秒"。
这个交换**只在"后台任务不参与用户当前答案"时才成立**：
一旦后台任务的结果要进当前回答，就必须当场同步（例如记忆写入 —— 写没写完直接决定这一轮能不能检索到）。

## 第二十二节：可观测性

**目标：知道系统此刻在发生什么。** 不是"出事了再翻日志"，是"随时能看"。

**【四个层次，逐层看现状】**

| 层 | 要什么 | 现状 |
|---|---|---|
| 1. 日志 | `logs/*.jsonl` | **已落地**。思维流、健康、世界、中央事件、自主性各有独立目录；`logs/central/events.jsonl` 是跨模块事件流 |
| 2. 指标 | 调用次数、延迟、成功率、熔断次数 | **部分落地**。插件侧有熔断计数与调用指标（`tests/stress` 的安全与对抗用例在测）；模块侧的"调用次数 / 成功率 / 平均延迟"**没有统一采集口** |
| 3. 追踪 | 每次请求的完整链路 | **部分落地**。`GET /api/central` 能看到这一轮的中央状态（阶段 / 实体 / 工具轨迹 / 健康），但**没有 trace id**，跨线程的后台任务串不进同一条链 |
| 4. 告警 | 异常时通知用户 | **部分落地**。健康系统四级治疗会在地化地改行为（缩短回答、降级工具）；面向用户的显式告警**没有** |

**【关键指标（该采但目前没统一采）】**

- **每次对话**：token 用量、耗时、工具调用链
- **每个模块**：调用次数、成功率、平均延迟
- **系统整体**：内存、显存、并发数

**【界面：设置页的"系统状态"面板 —— 未落地】**

目标形态：显示当前模型、内存占用、活跃任务、健康状态。
**现状：没有这个面板。** 现在能看到的"系统状态"只有设置页的工具/能力和 `GET /api/central` 的原始 JSON。

**【为什么把它写进设计哲学而不是 backlog】**

因为**没有它，前面二十一节都不可验证**。
"协同网络整体大于部分之和"、"健康系统在预防"、"精度在叠加" —— 这些判断都需要
**能实时看到每个模块在干什么**才成立。观测性不是运维附属品，
它是这套架构**能不能被证明在工作的前提**。
