# 小焦怎么"越用越强"、又不会越用越离谱

> 四个模块：`core/answer_gate.py`（答案闸门）｜`core/dual_check.py`（双模型交叉审校）｜`core/plugin_forge.py`（能力自增长）｜`core/task_runner.py`（任务级自主）
> 自测：`tools/test_answer_gate.py`(14) ｜ `tools/test_dual_check.py`(15) ｜ `tools/test_plugin_forge.py`(21) ｜ `tools/test_task_runner.py`(27)

## 一、为什么是这三件

市面上 AI 的短板不是"不会答"，是**答得具体却不真**、**能力不由你决定**、**自己审自己**。
这三件分别对着三处下手，而且每一处都不是靠提示词求模型自觉：

| 痛点 | 机制 | 谁说了算 |
| --- | --- | --- |
| 编造细节（比分/日期/链接/价格） | **答案闸门**：把可核查断言抽出来，逐条在本轮材料里找依据 | 载体（正则 + 材料比对） |
| 自己审自己（自评 B 却输出编造） | **双模型交叉审校**：换一个模型来审，判不一致才标注 | 另一个模型 |
| 能力固定（厂商发版才有） | **能力自增长**：缺能力就自己写插件，过静态检查 + 沙箱才落地 | 载体（ast + 子进程） |

## 二、答案闸门（`core/answer_gate.py`）

**只挑四类断言**：带单位的数值、比分、日期、网址/文件路径。人名地名不在这里判
（中文实体边界难切，硬判会大面积误报）。

**比对口径偏宽**：只在三条时强标注 —— ①本轮一点材料都没有；②≥3 处找不到依据；
③有 1~2 处但属于"用户会拿去用"的类型（比分/日期/链接/路径）。其余不标注，
因为每句都弹警告，用户会把它当背景噪声。

**绝不改正文**：标注只加在前面。改内容等于载体替用户重写事实，比标注危险。

实测（`tools/test_answer_gate.py`）：
- 「菏泽 +13°C」且材料里有 → 不标注；
- 「西班牙 1-0 阿根廷，2026年7月20日」且材料只是新闻列表 → 强标注；
- 用户自己在问题里说过的数字 → 不算模型编的（不标注）。

## 三、双模型交叉审校（`core/dual_check.py`）

**为什么不用原有的"元认知自评"**：那是同一个模型给自己打分，实测经常和真实质量对不上。

**怎么做**：出答模型写答案 → 另选一个模型（优先跟出答不同的）只看"问题 + 答案"，
三选一：一致 / 不一致 / 无法判断 + 一句理由。判不一致就在前面标注。

**只在高风险时审**（花一次模型调用的钱）：答案里有 ≥2 处可核查断言，或问题涉及钱/医疗/法律/时间承诺。

**措辞边界**：两个模型一致**不等于**内容正确（可能一起错），所以输出只说"另一个模型也这么说"，
不说"已核实"。失败（超时/连不上）一律 unknown，绝不拖慢回答。

## 四、能力自增长（`core/plugin_forge.py` + `plugins/forge.py`）

用户说「给我加个能 XX 的能力」→ 载体直接走 `forge_plugin`（不指望 4B 自己想得起来）：

```
说需求 → 生成插件代码 → 静态检查 →（不过就回喂错误自修，最多 2 轮）→ 子进程沙箱试跑 → 落地 plugins/gen_*.py
```

**四道关，没有一道是"模型说行就行"**：

| 关 | 查什么 | 不合格的后果 |
| --- | --- | --- |
| 静态检查（`ast`） | 插件契约三件套、import 白名单、危险调用（subprocess/eval/删文件） | 判死，不落地 |
| 契约措辞 | 工具名必须英文、说明里必须有「什么时候用」、parameters 是标准 JSON Schema | 判死或由载体补齐并记下"补了几处" |
| **撞名检查** | 声明的工具名和仓库里已有的撞不撞（撞了调用会被别人的插件接住） | 判死，回喂模型改名 |
| 沙箱试跑 | **另起子进程** import，调两个契约方法 + 用空参数真调一次 execute | 判死（绝不带进主进程） |
| 只加不删 | 文件名带时间戳，同名不覆盖 | 换名另存 |

**关键改造：模板优先（`forge_template`）—— 契约由载体写死，模型只写业务函数**

第一版是"让模型写整份插件"，实测**一次成功率只有 45.5%**（经验库 11 次里成 5 次）。
失败几乎都集中在"契约措辞 / 语法被截断 / 工具名用了中文"这些**与业务无关**的地方。
于是改成：模型只输出一个小函数（`def transform(text): ...`），
类、两个契约方法、`get_plugin`、说明、参数 schema 全部由载体拼装。

```
改前（自由生成）：5/11 = 45.5%
改后（模板优先）：5/5  = 100%（平均 5 秒/个，最长 16 秒）
实测需求：中文数字转换 / 统计字数行数 / 首字母大写 / 闰年判断 / 秒数换算
```

模板路径失败会**自动退回**自由生成，并把失败原因写进经验库（下次生成时作为教训注入）。

**真机跑通的那一次**（2026-10-27）：
```
need = 「把中文数字（一、二…十、百、千）转成阿拉伯数字」
9.5 秒 → ✅ 新能力已生成并落地 plugins/gen_cap_20261027_173718.py
重启后：工具表 102 → 103，cn_num_to_int 可调
三千零二十 → 3020 ｜ 一百零五 → 105 ｜ 一万零一 → 10001
```

**初版被下游抓出的三个毛病（已修，如实记下）**：
1. 工具名用了中文 → 契约自测不通过（工具名要能被准确调用）；
2. 载体补「什么时候用」的正则过宽，把**参数说明**也补了一遍 → 读起来是噪声；
   现在按 `"name":` 切块，每块只补工具级那一个 description；
3. **第二份自生成插件撞了已有工具名**（声明 `cn_num_to_int`，可它属于另一个插件）
   → 调用被别人的插件接住、报「这里没有这个工具」。现在落地前先查撞名。

**落地≠能用**：插件要重启（或热注册）才进工具表。这条在返回里明写，不假装已经生效。

## 五、自进化内核（`core/self_evolve.py` + `core/experience.py` + `plugins/evolve.py`）

前面四节是"手"和"尺子"，这一节是把它们接成**闭环**：看见红点 → 知道该动哪儿 → 记住这次教训。

```
评测/体检产出（三份实跑文件）
      ↓  diagnose()  归类成六种"病"，每种给出具体动作，按影响面×成本排序
改进清单（evolve_report 工具，对话里直接问「现在哪里最弱」）
      ↓  唯一的自动路径：缺能力 → forge_plugin（带静态检查 + 子进程沙箱）
经验库（logs/experience.jsonl，append-only）
      ↓  lessons(kind, keyword) → 注入下次生成的提示词
下次生成更少踩同一个坑
```

**六种病与优先级**（数字越小越先修）：

| 病 | 优先 | 能自动吗 | 典型动作 |
| --- | --- | --- | --- |
| 工具坏了（真报错） | 1 | 否 | 先 `--only <工具>` 复现，再按报错原文修本体 |
| 判据/路由漏了 | 2 | 否 | 把原话加进判据词表 + 补一条离线断言钉住 |
| 答案该有的东西没出现 | 3 | 否 | 补直答路径或补判据（别只改判据不改链） |
| 太慢 | 4 | 否 | 查这一轮档位、审校有没有被误触发 |
| 展示效果差 | 5 | 否 | 去噪规则补这一类行 |
| 需参数 / 没测过 / 缺条件 | 6~8 | 否 | 补沙箱用例 / 写清依赖代价 |

**经验库为什么单独一个文件**：对话记忆按语义相似检索，会捞回一堆闲聊；
经验库按 `kind + 关键词` 精确命中"同一类事栽在哪"，两者不能混。

**两个被实测打回来的点（已修）**：
1. **证据过期**：诊断起初照旧把 `archify_deliver`「未实测」列成待修项 —— 可那一条早就修好了，
   体检报告是旧的。现在报告会先查文件 mtime，超过 24 小时就提示「先重跑再诊断」；
2. **判分误报**：`evolve_report` 的输出是中文说明文本，通用判分把里面的"需要/缺…"当成报错 →
   被判成「缺配置」。按既定原则给它写了沙箱用例（看返回特征，不看字样）。

**真机验证**：对话里问「现在哪里最弱，下一步该改什么」→ 工具轨迹 `[evolve_report]`，
直接给出按优先级排序的改进清单（每条带证据与动作）。

## 六、无人值守：它自己按（`core/auto_evolve.py`）+ 经验复用（`core/skill_memory.py`）

前五节都缺一件事：**得有人去按**。这一节补上两样 ——
它自己在空闲时按诊断动手，以及把"做成过的事"变成可直接照抄的序列。

### 6.1 它自己按（auto_evolve）

```
每 6 小时看一次（可配 auto_evolve.interval_h）
   → 读 self_evolve.diagnose()
   → 跳过 24 小时内已试过的项
   → 只有「缺能力」类真的动手（走 forge，自带静态检查 + 子进程沙箱）
   → 其余类型只写「改进卡」到 logs/auto_evolve/cards/，不动源码
   → 每天最多行动 3 次（可配 per_day），历史落 logs/auto_evolve/history.jsonl
```

三条硬规矩：① 只有一类能自动动手（判据/答案/性能只出卡，不自动改 `core/` 与主程序）；
② 同一项 24 小时内不重试（否则在同一个坑上每 6 小时撞一次）；③ 诊断没红点就立刻返回。

启动点有个坑：真正被执行的启动脚本是 `start_xiaojiao.py`，它最后直接 `app.app.run(...)`，
**不走 `xiaojiao_app.main()`** —— 第一版把启动块写在 `main()` 里，实测启动日志里根本没有
「自我改进：已起」这一行。现在挂在启动器上。

### 6.2 经验复用（skill_memory）

一次**成功的多步任务**（≥2 个工具、无失败痕迹）固化成技能：
`问题 → 工具序列（名称+关键参数）→ 结果要点 → 耗时`。
下次遇到同类问题（2 字词覆盖率 ≥0.5），载体把旧序列摆进 system 一句话：
「上次同类问题用了这条序列「get → write_file」，2 步，5.5 秒。可以直接照它做。」

为什么这是真提升：实测错误几乎都集中在"选工具 + 拼参数"这一步（问天气去搜网页、
爬书去截图、写代码挑错模型）。把它自己踩出来的正确路径存下来，等于不再重复犯错。
判据宁可少记也不记脏：单工具不记、有失败痕迹不记、同一问题只留最近一条。

### 6.3 这一节被实测打回的两次

1. **自动动手拿垃圾需求开工**：`act()` 里用一串 replace 去"清洗"证据文本，结果取到 `x`
   → forge 拿 `x` 当需求，模型胡乱写了一份插件，而沙箱只校验"不抛异常、返回字符串"，
   于是**垃圾居然落了地**。现在需求提取只认「需求：…」「need：…」或引号短句，
   取不到就不动手；forge 也加了「<6 字符或纯符号 → 直接拒」。
2. **重复闸门对不同措辞失效**：
   「把中文数字（一、二…十、百、千）转成阿拉伯数字」vs
   「帮我写个小工具，把'九亿零五万'转换成纯阿拉伯数字，然后告诉我结果」
   是同一件事，可 2 字词覆盖率只有 40% → 又长出一个重复工具。现在先剔掉
   "帮我/写个小工具/然后/告诉我"这些外壳词再比内核词，并增加一条
   "与已有工具说明的内核词重合"判据。

## 七、任务级自主：给一件事，而不是问一句话（`core/task_runner.py`）

前面六节管的是"这一句答得真不真"。这一节换一种交付形态：**用户给的是一件要好几步才能做成的事**。

**为什么载体必须自己接**：实测把这句交给模型 ——
「把 https://www.gutenberg.org/ebooks/1342 这个页面的内容全部抓下来存到 G:\dzs\task_test」
它回一句"好的，我来帮你抓"，工具轨迹是空的；用户以为在跑，其实什么都没发生。
所以"多步目标"由载体的规则接住（`_task_intent`：出现「全部/逐条/批量/一口气/做完」+ 动作词），
落到 `task_runner`，而不是求模型自觉。

```
给目标 → 拆解（规则优先，规则拿不准才问模型）→ 逐步执行（失败按同族工具换路）
      → 每步验收（程序化判得了的才判）→ 落盘 logs/tasks/<id>.json（每步都落）
      → 完成/如实失败 → 固化成技能（≥2 步且无失败痕迹）
```

**四条硬规矩**

1. **拆解先走规则**：抓取+落盘、天气取数、电子书、公网 IP 这些能由载体定死的，绝不去问模型
   （问模型 = 慢、且同一句话每次拆得不一样）。规则拿不准的（画图要 spec）才交给模型拆，
   且**只接受白名单里的工具名** —— 模型编出来的名字直接丢掉。
2. **失败就换路，换完还不行就停在那一步**：`app._tool_fallback_for()` 的同族链最多试 3 个，
   全失败则整条任务 `failed`，`why` 写成「第 N 步（工具）没做成：…」，**不许说成完成**。
3. **验收只做程序化判得了的**：文件真在（还看字节数）、有 IP 样式、有气温数字、返回无非空失败标记。
   判据不认识的**不假装通过** —— 记成「验收没把握」并把整个任务标 `partial`。
4. **状态是磁盘上的事实**：`logs/tasks/<id>.json` 原子落盘（`.tmp` + `os.replace`），
   进程被杀也能`resume` 接着跑；`task_status` / `task_list` 直接读它，不靠模型复述。
5. **做完要主动说**：后台跑完只落盘、等人来问，等于"做了没交付"。所以完成/失败会写进
   一次性播报位（`notified` 标记），下一次对话开头自动贴在回答最前面，取走即失效 ——
   不重复念、不堆积。

**实测踩到并修掉的三个坑**（都是"看起来成功"的坑）

- **成功的抓取被判失败**：抓取类工具返回 `{"status":200,"url":…,"content":…,"error":""}`，
  第一版用"文本里有 error 字样"判，`error` 字段**存在但为空**，于是 2 步任务在第 1 步就 `failed`。
  现在先 `json.loads` 按 `status`/`error` **值**判，解析不了才退回文本，且文本判据剔掉了
  `error`/`失败`/`不可用` 这些到处都出现的泛词。
- **存下去的是返回外壳不是正文**：落盘那步把 `str(res)` 整串写进用户文件，文件开头是
  `{"status": 200, "url": …}`。现在只取 `content`/`text` 字段；文件名也从固定 `_task_body.md`
  改成按 URL 起名（`www.gutenberg.org_ebooks_1342.md`），并且验收会检查「文件在且 ≥200 字节」。
- **同一页存了两份**：任务跑完后，聊天那条"抓取直通"兜底又抓了一遍并另存一个文件，
  还把回答换成了兜底那个路径。现在这一轮已经开过任务（轨迹里有 `task_start`），兜底一律让路。
- **外壳被当成技能**：`task_start` 只是"把活交出去"，可出口处把它当步骤进了技能库
  （序列 = `[task_start]`，照它做只会再开一个任务），同一个目标因此存了两条。现在外壳工具
  一出现就不固化，并说明"真实步骤由任务自己固化"。

实测（live 副本，同一个真实目标连跑三次）：

| 轮次 | 现象 | 结果 |
| --- | --- | --- |
| 第 1 次 | 成功的抓取被判失败 | `failed` 0/2 步 |
| 第 2 次 | 判据修好，但存的是 JSON 外壳、目录里两份 | `done` 2/2 步（`partial` 无） |
| 第 3 次 | 修好落盘与让路 | `done` 2/2 步，目录 **1 个**文件 5378 字节，正文开头是页面正文 |

## 八、怎么验证

一次跑完全部（126 个文件）：每个文件单独子进程 + 超时，没通过的**串行复测一次**再算数
（并行会抢端口/抢模型，不重测就分不清"真坏"和"被挤坏"）：

```bash
python tools/run_all_tests.py                  # 5 路并行、150 秒/文件、失败自动复测 → docs/test-report.md
python tools/run_all_tests.py --jobs 1         # 串行（最慢但最干净）
python tools/run_all_tests.py task_runner      # 只跑名字里带这个的
```

单跑几个关键的：

```bash
python tools/test_task_runner.py     # 35 项：规则拆解 / 执行验收 / 失败换路 / partial / resume / 播报 / 技能固化
python tools/test_silent_evolve.py   # 23 项：技能库 + 无人值守（宁少不脏 / 不空转 / 只走白名单）
python tools/test_self_evolve.py     # 28 项：经验库 + 诊断 + 文档类 + 只加不删
python tools/test_plugin_forge.py    # 21 项：静态检查 / 沙箱 / 自修 / 重复闸门 / 只加不删
python tools/test_answer_gate.py     # 14 项：挑断言 / 有依据不标 / 正文不动
python tools/test_dual_check.py      # 15 项：谁该被审 / 审的人不是自己 / 失败即跳过
python tools/eval_xiaojiao.py --save # 端到端 41 项 + 趋势
python tools/health_capability.py --save   # 工具真机体检
```

## 九、边界（如实说）

- **闸门不是真理裁判**：它只说"这条我找不到依据"，从不说"这条错了"；
- **双模型一致≠正确**：同基座的不同量化会一起错；
- **自增长受模型能力限制**：4B 一次成功率大约一半，靠自修复拉到可用；写不对就不落地，
  宁可没有这个能力，也不往仓库塞坏插件；
- **自增长只写 `plugins/gen_*.py`**：不碰 `core/`、不碰主程序 —— 这是硬的，不给开关。
- **任务拆解的天花板在规则覆盖**：规则认得的几类（抓取落盘/天气/电子书/单工具取数）稳；
  规则不认得的交给模型拆，模型拆歪了就换路、换完还不行就如实失败 —— 不会为了"看起来做完"硬凑。
- **验收只到能程序化判的程度**：「这一页内容是否真的是用户想要的那一页」这类语义判断，
  载体判不了，只能靠抓取校验（风控页识别）和用户复看。
- **没人替它决定"该不该做"**：`task_start` 只执行用户交出的目标，不自选目标。自动挑活干的是
  第五节那个 6 小时循环，且只允许「缺能力」一类真动手。
