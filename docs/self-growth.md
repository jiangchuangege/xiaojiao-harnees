# 小焦怎么"越用越强"、又不会越用越离谱

> 三个模块：`core/answer_gate.py`（答案闸门）｜`core/dual_check.py`（双模型交叉审校）｜`core/plugin_forge.py`（能力自增长）
> 自测：`tools/test_answer_gate.py`(14) ｜ `tools/test_dual_check.py`(14) ｜ `tools/test_plugin_forge.py`(20)

## 一、为什么是这三件

市面上 AI 的短板不是"不会答"，是**答得具体却不真**、**能力不由你决定**、**自己审自己**。
这三件分别对着三处下手，而且每一处都不是靠提示词求模型自觉：

| 痛点 | 机制 | 谁说了算 |
| --- | --- | --- |
| 编造细节（比分/日期/链接/价格） | **答案闸门**：把可核查断言抽出来，逐条在本轮材料里找依据 | 载体（正则 + 材料比对） |
| 自己审自己（自评 B 却输出编造） | **双模型交叉审校**：换一个模型来审，判不一致才标注 | 另一个模型 |
| 能力固定（厂商发版才有） | **能力自增长**：缺能力就自己写插件，过静态检查 + 沙箱才落地 | 载体（ast + 子进程） |

## 二、答案闸门（`core/answer_gate.py`）

**只挑四类断言**：带单位的数值、比分、日期、网址/文件路径。人名地名不在这里判
（中文实体边界难切，硬判会大面积误报）。

**比对口径偏宽**：只在三条时强标注 —— ①本轮一点材料都没有；②≥3 处找不到依据；
③有 1~2 处但属于"用户会拿去用"的类型（比分/日期/链接/路径）。其余不标注，
因为每句都弹警告，用户会把它当背景噪声。

**绝不改正文**：标注只加在前面。改内容等于载体替用户重写事实，比标注危险。

实测（`tools/test_answer_gate.py`）：
- 「菏泽 +13°C」且材料里有 → 不标注；
- 「西班牙 1-0 阿根廷，2026年7月20日」且材料只是新闻列表 → 强标注；
- 用户自己在问题里说过的数字 → 不算模型编的（不标注）。

## 三、双模型交叉审校（`core/dual_check.py`）

**为什么不用原有的"元认知自评"**：那是同一个模型给自己打分，实测经常和真实质量对不上。

**怎么做**：出答模型写答案 → 另选一个模型（优先跟出答不同的）只看"问题 + 答案"，
三选一：一致 / 不一致 / 无法判断 + 一句理由。判不一致就在前面标注。

**只在高风险时审**（花一次模型调用的钱）：答案里有 ≥2 处可核查断言，或问题涉及钱/医疗/法律/时间承诺。

**措辞边界**：两个模型一致**不等于**内容正确（可能一起错），所以输出只说"另一个模型也这么说"，
不说"已核实"。失败（超时/连不上）一律 unknown，绝不拖慢回答。

## 四、能力自增长（`core/plugin_forge.py` + `plugins/forge.py`）

用户说「给我加个能 XX 的能力」→ 载体直接走 `forge_plugin`（不指望 4B 自己想得起来）：

```
说需求 → 生成插件代码 → 静态检查 →（不过就回喂错误自修，最多 2 轮）→ 子进程沙箱试跑 → 落地 plugins/gen_*.py
```

**四道关，没有一道是"模型说行就行"**：

| 关 | 查什么 | 不合格的后果 |
| --- | --- | --- |
| 静态检查（`ast`） | 插件契约三件套、import 白名单、危险调用（subprocess/eval/删文件） | 判死，不落地 |
| 契约措辞 | 工具名必须英文、说明里必须有「什么时候用」、parameters 是标准 JSON Schema | 判死或由载体补齐并记下"补了几处" |
| **撞名检查** | 声明的工具名和仓库里已有的撞不撞（撞了调用会被别人的插件接住） | 判死，回喂模型改名 |
| 沙箱试跑 | **另起子进程** import，调两个契约方法 + 用空参数真调一次 execute | 判死（绝不带进主进程） |
| 只加不删 | 文件名带时间戳，同名不覆盖 | 换名另存 |

**关键改造：模板优先（`forge_template`）—— 契约由载体写死，模型只写业务函数**

第一版是"让模型写整份插件"，实测**一次成功率只有 45.5%**（经验库 11 次里成 5 次）。
失败几乎都集中在"契约措辞 / 语法被截断 / 工具名用了中文"这些**与业务无关**的地方。
于是改成：模型只输出一个小函数（`def transform(text): ...`），
类、两个契约方法、`get_plugin`、说明、参数 schema 全部由载体拼装。

```
改前（自由生成）：5/11 = 45.5%
改后（模板优先）：5/5  = 100%（平均 5 秒/个，最长 16 秒）
实测需求：中文数字转换 / 统计字数行数 / 首字母大写 / 闰年判断 / 秒数换算
```

模板路径失败会**自动退回**自由生成，并把失败原因写进经验库（下次生成时作为教训注入）。

**真机跑通的那一次**（2026-10-27）：
```
need = 「把中文数字（一、二…十、百、千）转成阿拉伯数字」
9.5 秒 → ✅ 新能力已生成并落地 plugins/gen_cap_20261027_173718.py
重启后：工具表 102 → 103，cn_num_to_int 可调
三千零二十 → 3020 ｜ 一百零五 → 105 ｜ 一万零一 → 10001
```

**初版被下游抓出的三个毛病（已修，如实记下）**：
1. 工具名用了中文 → 契约自测不通过（工具名要能被准确调用）；
2. 载体补「什么时候用」的正则过宽，把**参数说明**也补了一遍 → 读起来是噪声；
   现在按 `"name":` 切块，每块只补工具级那一个 description；
3. **第二份自生成插件撞了已有工具名**（声明 `cn_num_to_int`，可它属于另一个插件）
   → 调用被别人的插件接住、报「这里没有这个工具」。现在落地前先查撞名。

**落地≠能用**：插件要重启（或热注册）才进工具表。这条在返回里明写，不假装已经生效。

## 五、自进化内核（`core/self_evolve.py` + `core/experience.py` + `plugins/evolve.py`）

前面四节是"手"和"尺子"，这一节是把它们接成**闭环**：看见红点 → 知道该动哪儿 → 记住这次教训。

```
评测/体检产出（三份实跑文件）
      ↓  diagnose()  归类成六种"病"，每种给出具体动作，按影响面×成本排序
改进清单（evolve_report 工具，对话里直接问「现在哪里最弱」）
      ↓  唯一的自动路径：缺能力 → forge_plugin（带静态检查 + 子进程沙箱）
经验库（logs/experience.jsonl，append-only）
      ↓  lessons(kind, keyword) → 注入下次生成的提示词
下次生成更少踩同一个坑
```

**六种病与优先级**（数字越小越先修）：

| 病 | 优先 | 能自动吗 | 典型动作 |
| --- | --- | --- | --- |
| 工具坏了（真报错） | 1 | 否 | 先 `--only <工具>` 复现，再按报错原文修本体 |
| 判据/路由漏了 | 2 | 否 | 把原话加进判据词表 + 补一条离线断言钉住 |
| 答案该有的东西没出现 | 3 | 否 | 补直答路径或补判据（别只改判据不改链） |
| 太慢 | 4 | 否 | 查这一轮档位、审校有没有被误触发 |
| 展示效果差 | 5 | 否 | 去噪规则补这一类行 |
| 需参数 / 没测过 / 缺条件 | 6~8 | 否 | 补沙箱用例 / 写清依赖代价 |

**经验库为什么单独一个文件**：对话记忆按语义相似检索，会捞回一堆闲聊；
经验库按 `kind + 关键词` 精确命中"同一类事栽在哪"，两者不能混。

**两个被实测打回来的点（已修）**：
1. **证据过期**：诊断起初照旧把 `archify_deliver`「未实测」列成待修项 —— 可那一条早就修好了，
   体检报告是旧的。现在报告会先查文件 mtime，超过 24 小时就提示「先重跑再诊断」；
2. **判分误报**：`evolve_report` 的输出是中文说明文本，通用判分把里面的"需要/缺…"当成报错 →
   被判成「缺配置」。按既定原则给它写了沙箱用例（看返回特征，不看字样）。

**真机验证**：对话里问「现在哪里最弱，下一步该改什么」→ 工具轨迹 `[evolve_report]`，
直接给出按优先级排序的改进清单（每条带证据与动作）。

## 六、怎么验证

```bash
python tools/test_answer_gate.py     # 14 项：挑断言 / 有依据不标 / 正文不动
python tools/test_dual_check.py      # 14 项：谁该被审 / 审的人不是自己 / 失败即跳过
python tools/test_plugin_forge.py    # 20 项：静态检查 / 沙箱 / 自修 / 只加不删
python tools/eval_xiaojiao.py --save # 端到端 41 项 + 趋势
python tools/health_capability.py --save   # 103 个工具真机体检
```

## 七、边界（如实说）

- **闸门不是真理裁判**：它只说"这条我找不到依据"，从不说"这条错了"；
- **双模型一致≠正确**：同基座的不同量化会一起错；
- **自增长受模型能力限制**：4B 一次成功率大约一半，靠自修复拉到可用；写不对就不落地，
  宁可没有这个能力，也不往仓库塞坏插件；
- **自增长只写 `plugins/gen_*.py`**：不碰 `core/`、不碰主程序 —— 这是硬的，不给开关。
