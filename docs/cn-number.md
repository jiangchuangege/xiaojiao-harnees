# 中文数字翻译：为什么这种活不让模型干

> 代码：`core/cn_number.py`（规则为主的翻译）
> 调用方：`core/calc.py` —— 载体直算那一路
> 相关：[`raw-material.md`](raw-material.md)（给原料不给成品）

---

## 1. 问题

用户说「三千二百五十六乘以二」「两万三够不够」—— 这是**算钱**的场景。

中文数字是**确定性的**：「三千二百五十六」就是 3256，只有一个答案。
它跟阿拉伯数字的差别只是**写法**，不是**语义推理** —— 这种活本来就不该让模型干。

## 2. 实测：4B 在这里不稳

代码里记着实测结论：

> 4B 对「两万三」「一千二」这类**口语省略写法**非常不稳 ——
> **实测会把「两万三」翻成 2300 或 20300**（漏一位 / 多一位）。

而用户是拿它去**算钱**的。差一位就是十倍。

## 3. 做法：规则为主，模型只兜底，且必须过校验

| 情况 | 谁来做 |
|---|---|
| 规则覆盖的写法（「三千二百五十六」「两万三」「一千二」…） | **规则直接翻** —— 零延迟、必然正确 |
| 规则覆盖不到的极端写法 | 才让 4B 给一个**纯数字表达式** |
| 模型给的那个表达式 | **必须过载体的格式校验**才采信；不过就当没给 |

这条分工和整个项目一致：**确定性的活归载体，措辞归模型。**
数字翻译是确定性的，所以它是载体的活 —— 模型只负责那个极端兜底。

## 4. 对外接口

```python
cn_to_int(s)      # 「三千二百五十六」→ 3256
to_arabic(s)      # 整句里的中文数字换成阿拉伯数字
has_cn_number(t)  # 这句话里有没有中文数字（没有就不用走这条链）
CN_CHARS          # 中文字符表
```

## 5. 如实标注

1. **它不解析数学表达式**，只做**数字写法**的翻译；算式求值在 `core/calc.py`。
2. **模型兜底那一路不是"必然正确"** —— 它靠的是"给纯数字表达式 + 过格式校验"，
   校验只管**格式对不对**，管不了**语义有没有翻错**。
3. 规则的覆盖面是**枚举式**的（能列的写法都列了），
   遇到没列到的方言写法会落到模型兜底 —— 这一层的能力边界没有全量实测过。
