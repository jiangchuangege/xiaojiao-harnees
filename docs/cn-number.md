# 中文数字翻译：确定性的活为什么归载体

> 代码：`core/cn_number.py`（规则为主的翻译）
> 调用方：`core/calc.py` —— 载体直算那一路
> 相关：[`raw-material.md`](raw-material.md)（给原料不给成品）

---

## 1. 问题

用户说「三千二百五十六乘以二」「两万三够不够」—— 这是**算钱**的场景。

中文数字是**确定性的**：「三千二百五十六」就是 3256，只有一个答案。
它跟阿拉伯数字的差别只是**写法**，不是**语义推理**。

> ⚠️ **本文标题改过一次**。原来叫「为什么这种活不让模型干」，
> 隐含的前提是"模型干不了" —— **实测证明模型干得了**（见下一节）。
> 真正的理由是<b>"确定性问题该用确定性办法"</b>，不是"模型做不到"。

## 2. 实测：模型其实翻得对（**这一节改过，原来写错了**）

> ⚠️ **本文第一版在这里写着**：「4B 对『两万三』『一千二』这类口语省略写法非常不稳，
> 实测会把『两万三』翻成 2300 或 20300」。
> **那句话是从 `core/cn_number.py` 的代码注释里抄的，我没有亲自测过。**
> 用户质疑「这不是可以实现吗」，于是直接测了一遍 —— **结果是模型全对。**

实测（`temperature=0`，直接问大脑，只取一行数字）：

| 输入 | 模型答 | 期望 | 耗时 |
|---|---|---|---|
| 三千二百五十六 | **3256** ✅ | 3256 | 0.4s |
| 两万三 | **23000** ✅ | 23000 | 0.3s |
| 一千二 | **1200** ✅ | 1200 | 0.3s |
| 三万五 | **35000** ✅ | 35000 | 0.3s |
| 十五万 | **150000** ✅ | 150000 | 0.3s |
| 两千三百万 | **23000000** ✅ | 23000000 | 0.3s |
| 一点五万 | **15000** ✅ | 15000 | 0.3s |
| 百分之三十 | **30** ✅ | 30 | 0.2s |
| 负的两万三 | **-23000** ✅ | -23000 | 0.3s |
| 二十三点五 | **23.5** ✅ | 23.5 | 0.2s |

**10 / 10 全对**，包括代码注释里点名说会翻错的那几个。

**结论：代码注释里那句"实测会翻错"，在当前这套模型 + 提示词下复现不出来。**
它可能来自更早的模型或更早的提示词 —— **但没有留原始记录，所以只能标成"现在复现不出来"，
不能说它当年也错。**

## 3. 那为什么还要规则？（理由换了）

既然模型翻得对，为什么不让模型干？**理由不是"模型做不到"，而是"规则更适合这种问题"：**

| | 规则 | 模型 |
|---|---|---|
| 正确性 | **必然正确**（覆盖到的写法没有第二种答案） | 实测全对，但本质是"大概率对" |
| 延迟 | **零**（本地字符串处理） | 每次 0.2–0.4 秒 + 一次模型调用 |
| 稳定性 | 同一输入永远同一输出 | 取决于模型版本 / 提示词 / 温度 |
| 可核对 | 规则读得懂、能单测 | 只能靠样例回归 |

一句话：**中文数字是确定性问题，确定性问题用确定性办法解** ——
这是"该用哪个"的选择，**不是"模型不会"**。

实测也确认这个分工划算：**规则那一路 23/23 全对**（含 `两万三`=23000、`一千二`=1200、`三万五`=35000）；
规则覆盖得到，就**不需要花那次模型调用**。模型兜底只留给规则没覆盖的写法。

## 5. 如实标注

1. **它不解析数学表达式**，只做**数字写法**的翻译；算式求值在 `core/calc.py`。
2. **模型兜底那一路不是"必然正确"** —— 它靠的是"给纯数字表达式 + 过格式校验"，
   校验只管**格式对不对**，管不了**语义有没有翻错**。
3. 规则的覆盖面是**枚举式**的（能列的写法都列了），
   遇到没列到的方言写法会落到模型兜底 —— 这一层的能力边界没有全量实测过。
