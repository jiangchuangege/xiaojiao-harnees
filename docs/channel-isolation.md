# 渠道隔离：把某个接入通道关成"只能聊天"

> 代码：`core/channel_policy.py`（策略）· `xiaojiao_app.py`（两道闸 + 请求钩子）
> 自测：`tools/test_channel_policy.py`（24 项，已接入 CI）

---

## 1. 为什么需要它（真实的安全问题）

**小焦不是一个聊天机器人。** 它手上有：

- `run_command`（跑命令）
- `read_file` / `write_file` / `edit_file`（读写文件）
- **自主行为**（自己逛网、自己决定发起动作）

所以一旦把它接到<b>"别人能给它发消息"</b>的地方（微信 / QQ / 任何 IM），
就等价于**把电脑的钥匙递出去**：谁能给那个号发消息，谁就可能驱动机器干活。

**"不能删任何文件"那条红线挡不住这件事** —— 它是硬的，但 `run_command` 能做的事远不止删文件。

所以要的是：**按接入通道限权** —— 网页（自己人）全权，外部通道只能聊天。

---

## 2. 怎么用（桥接方只加一个请求头）

```http
POST /api/chat
X-Xiaojiao-Channel: wechat
```

然后在操控文件 `xiaojiao_control.json` 里写策略：

```json
{
  "channels": {
    "wechat": { "tools": [] },
    "family": { "tools": ["list_files", "web_search"] }
  }
}
```

| 写法 | 效果 |
|---|---|
| `"tools": []` | **纯聊天**（一个工具都不给）—— 推荐给微信这类通道 |
| `"tools": ["a", "b"]` | 只给这两个 |
| **没写这个渠道** | **按最严处理 = 纯聊天**（默认拒绝） |
| 本机请求（**不带这个头**） | **完全不受限**（网页是自己人） |

---

## 3. 两道闸，缺一不可

| | 在哪 | 作用 |
|---|---|---|
| **闸① 工具表** | `_plan_tools()` | 这条通道下**模型根本看不到**工具 —— 不会去点、不会去编 |
| **闸② 执行** | `run_tool()` | 即使模型硬编了一个工具名，**到执行这一步直接拒绝** |

**⚠️ 只做闸① 是假隔离。** 4B 会硬编工具名（实测出现过），**看不到 ≠ 调不到**。
执行闸是硬防线，不依赖模型守规矩。

两道闸都走真实代码路径验过（`tools/test_channel_policy.py` 的 [C] 与 [E] 组）：
渠道下 `run_command` / `write_file` / `list_files` 全部被拒；
渠道下工具表为 **0**（连"意图认不出来就给核心集"那条兜底也挡住了）。

---

## 4. 三条设计原则

1. **默认拒绝**。没声明策略的渠道 → 纯聊天。想放开得**显式去配置里加白名单**。
   反过来（默认全开、要缩自己去缩）迟早出事。
2. **失败朝安全方向倒**。配置读不到、写坏了、格式不对 → **一律按最严（纯聊天）处理**。
3. **必须清状态**。Flask 线程是复用的，请求结束不清渠道 = **把限权带到下一个请求上（串权）**。
   所以有 `teardown_request` 兜着。

---

## 5. ⚠️ 它不是身份认证（必须说清）

`X-Xiaojiao-Channel` 是**桥接方自己填的**。它能防的是：

- ✅ **我配置错了**，把危险工具暴露给了外部通道
- ❌ **不能防有人伪造这个头**（伪造 `wechat` 反而更安全，因为被限权）

**真正的鉴权必须在桥那边做**：只允许**你白名单里的 userid** 能触发。
两者是**互补**的：桥负责"谁在说话"，渠道策略负责"这条通道最多能干到哪"。

---

## 6. 还要注意的

- **渠道策略只管工具**，不管别的东西。比如"它主动逛网"那条链最终也是通过工具执行的 → 会被闸②挡住。
- **本机网页不受影响**：不带请求头的都是本机请求，行为与从前完全一致
  （自测 [A] 组和 [E] 组的对照组专门盯这件事 —— 加隔离不能把自家弄瘫）。
- **目前没有现成的微信桥**。这份文档给的是"接口与安全边界"，桥要自己写
  （收消息 → 带 `X-Xiaojiao-Channel` 头调 `/api/chat` → 把回复发回去）。
  飞书 / 钉钉已有的是**只出不进的通知通道**（`autonomy.webhooks`），不是双向对话。

---

## 7. 如实标注

1. **微信三条路合规性不同**：个人微信**没有官方 API**，第三方方案属逆向、**违反微信协议会封号**；
   企业微信与公众号有官方 API。**本模块不解决合规问题**，只解决"接上去之后它能干到哪"。
2. **公众号被动回复有 5 秒超时**，而小焦回一句常常要 6～35 秒（要检索、要调工具）——
   **几乎必然超时**，得靠客服消息异步补推。企业微信自建应用在这方面宽裕得多。
3. **白名单是"名字级"的**，不做参数级校验。比如你把 `web_search` 放进白名单，
   它就真的能联网搜 —— **放哪些工具进白名单要自己掂量**。
4. **我没有实测过真实的微信桥**（本机没有微信环境）。本模块的验证范围是：
   策略判定 + 两道闸在真实代码路径上生效，**不含真实 IM 链路**。
